description: "Move to a new image tag: run the migrations, recreate the app services, leave the data untouched."

Upgrading is a tag change plus a migration run. A new image can carry pending
schema **migrations**; a one-shot runner applies the chain before the app
services start, and each container refuses to serve on an out-of-date database
(the [boot gate](#the-boot-gate)). The image carries no state, so the data
volumes are never touched — only the app containers are replaced.

## Upgrade the Compose bundle

<Steps>
  <Step title="Snapshot the database first">
    A migration rolls **forward** only — there are no down-migrations. Before an
    upgrade that carries schema changes, take a Postgres snapshot (a managed
    provider's point-in-time restore, or `pg_dump`) so a bad release is a restore
    away. Recovery is restore-then-re-migrate, never a rollback.
  </Step>
  <Step title="Pin the new tag">
    Set `TAI_VERSION` in `.env` to the release you are moving to.

    ```bash TAI_VERSION in .env
    TAI_VERSION=1.6.33
    ```
  </Step>
  <Step title="Pull it">
    ```bash
    docker compose pull
    ```
  </Step>
  <Step title="Run the migrations">
    ```bash
    docker compose run --rm db-migrate
    ```

    The one-shot `db-migrate` service runs `tai db migrate`, which applies every
    pending migration across every component — the core chain, each installed
    plugin that owns one, and each plugin the manifest loads — in order, recording each in the `tai_schema_history`
    table. It is idempotent: a run with nothing pending reports so and exits `0`.
    Preview a run first with `docker compose run --rm db-migrate db migrate --plan`,
    which lists the pending files without touching the database.
  </Step>
  <Step title="Recreate the app services only">
    ```bash
    docker compose run --rm config-init
    docker compose up -d --no-deps serve backend metrics
    ```

    `config-init` hands `config/` to the image's user, as a full `up` does before
    the app services start. `--no-deps` then recreates the three app services
    against the new image without restarting Postgres or Redis, so the datastores
    — and their volumes — stay up.
  </Step>
</Steps>

<Note>
Read the release notes before pinning. A release that needs a step beyond the
migration run — a data backfill, a manual expand/contract cutover — names it.
</Note>

## Move the Langfuse stack to 4.x

The `compose/langfuse/` stack runs Langfuse 4.x, and the monitoring plugin
(`tai42-monitoring-langfuse` 6.0.0) needs a 4.x server. The move has no migration
variables: it replaces the stack's data.

<Steps>
  <Step title="Stop the stack and remove its volumes">
    ```bash
    docker compose -f compose/langfuse/docker-compose.yml down --volumes
    ```

    This removes `langfuse-postgres-data`, `langfuse-clickhouse-data`,
    `langfuse-clickhouse-logs`, `langfuse-minio-data` and `langfuse-redis-data`
    (prefixed `tai-langfuse_` under the default project name, or the `-p` name you use).
  </Step>
  <Step title="Pull the 4.x images">
    ```bash
    docker compose -f compose/langfuse/docker-compose.yml pull
    ```
  </Step>
  <Step title="Start the stack">
    ```bash
    docker compose -f compose/langfuse/docker-compose.yml up -d
    ```
  </Step>
</Steps>

Data recorded under 3.x is not carried over. The `LANGFUSE_INIT_*` values re-create
the same organisation, project and keys, so `config/.env` and the collector's
credential need no change.

## Recreate the states schema

A release can rewrite the states baseline in place. On an existing deployment the
[boot gate](#the-boot-gate) then refuses to start with:

```text
database schema is out of date — refusing to start: states: checksum mismatch on version(s) 1. Run 'tai db migrate' to apply the pending migrations, then restart.
```

and `tai db migrate` refuses too:

```text
Error: component 'states' version 1 ('baseline') was applied with checksum <recorded> but is now <current>; the chain has been rewritten
```

The step runs on the database the `states` component is bound to
(`TAI_DB_BINDING_STATES`, the `default` database unless set; in the Compose bundle the
`postgres` service, user and database `${POSTGRES_USER:-tai}` / `${POSTGRES_DB:-tai}`).
It drops every states table: `state_outbox`, `state_writes`, `state_applied_ops`,
`state_subject_aliases`, `state_records`, `state_attachments`, `state_templates` and
`state_declarations`, the pending saves among them, and the catalog version sequence
`state_catalog_versions`. Their data is lost.

<Steps>
  <Step title="Stop the app services">
    ```bash
    docker compose stop serve backend
    ```

    Compose prints each container as it stops.
  </Step>
  <Step title="Drop the states schema and its history rows">
    ```bash
    docker compose exec -T postgres psql -U "${POSTGRES_USER:-tai}" -d "${POSTGRES_DB:-tai}" -v ON_ERROR_STOP=1 <<'SQL'
    BEGIN;
    DROP TABLE state_outbox, state_writes, state_applied_ops, state_subject_aliases, state_records,
      state_attachments, state_templates, state_declarations;
    DROP SEQUENCE state_catalog_versions;
    DELETE FROM tai_schema_history WHERE component = 'states';
    COMMIT;
    SQL
    ```

    psql prints `BEGIN`, `DROP TABLE`, `DROP SEQUENCE`, `DELETE 1` and `COMMIT`. On any
    error psql stops, the transaction rolls back and nothing is dropped.
  </Step>
  <Step title="Apply the baseline">
    ```bash
    docker compose run --rm db-migrate
    ```

    It prints `Applied states 0001_baseline.` and `Applied 1 migration(s).`
  </Step>
  <Step title="Start the services">
    ```bash
    docker compose up -d
    ```

    The gate passes and the services start.
  </Step>
</Steps>

## The boot gate

Each `serve` and `backend` container checks, at startup and on every reload, that
every schema chain it depends on is fully applied: the core `skeleton` and `states`
chains, and the chain of every plugin the manifest loads, however that plugin is
installed, editable installs included. `tai setup --recover` runs the same check
before it imports any manifest module. A core chain, or a plugin chain under the
plugin's own name, whose component database is not configured is not checked. A plugin
chain on a declared [component binding](/concepts/config-and-secrets#component-bindings)
is always checked: an unconfigured bound database refuses boot and names the missing
setting. A pending migration or a rewritten (checksum-mismatched) chain is a **loud
refusal**, not a half-migrated serve:

```text
database schema is out of date — refusing to start: skeleton: 1 pending (0002_add_index.sql). Run 'tai db migrate' to apply the pending migrations, then restart.
```

The fix is the message: run the migration step above, then let the container
restart. If you recreate the app services before running `db-migrate`, they refuse
to boot with exactly this message — run the migrations and they come up. Running
`db-migrate` before the app services (the step order above) avoids the refusal
entirely. A checksum mismatch on the `states` chain is fixed by
[recreating the states schema](#recreate-the-states-schema).

A reload the gate refuses answers `500` with this message as its `error`, and the
server keeps serving its current configuration. `tai setup --recover` prints it as
`Error: …` and exits non-zero.

## Runtime-installed plugins

An image upgrade replaces the **core** only. Plugins added at runtime through the
[marketplace](/concepts/marketplace) live in the server's plugin prefix
(`TAI_PLUGINS_PREFIX`), not in the image, so **they do not update with a new image
tag** — a freshly pinned image boots with the same plugin versions the prefix
already holds.

Update them as a step of their own, after the image upgrade:

```bash
tai plugins upgrade --all
```

This resolves each installed plugin to the newest version compatible with the
core you are now running and installs it into the same persistent prefix. A
**router** or **middleware** plugin — and a channel's inbound webhook route — comes
live on the next reload / config-apply, not on a container restart: the epoch
rebuild that a reload runs re-imports the plugin package and its route-sibling
modules and re-registers the declared routes, so an upgraded router or middleware
is serving once that reload lands.

The image pins its own core versions as a pip/uv constraints file at
`/opt/tai/constraints.txt` and sets `PIP_CONSTRAINT`/`UV_CONSTRAINT` to it, so any
install — a marketplace install, `python -m pip install` by hand, or a derived
image's build step — that would move a core package (`tai42-contract`, `tai42-kit`,
`tai42-skeleton`, `tai42-cli`, or any other package the image ships) off the image's
version is refused by the resolver, never silently downgraded or upgraded. An
incompatible plugin fails loudly at install:

```text
ERROR: Cannot install tai42-monitoring-langfuse==3.0.3 because these package versions have conflicting dependencies.
    The user requested (constraint) tai42-contract==14.0.0
ERROR: ResolutionImpossible: for help visit https://pip.pypa.io/en/latest/topics/dependency-resolution/#dealing-with-dependency-conflicts
```

The venv is root-owned, so a direct install into it runs as root — a derived image's
`USER root` build step, or `docker exec -u 0` into a running container. The
marketplace installer writes to its own `--prefix` and is unaffected. After a manual
or derived-image install, run `python -m pip check` to confirm the environment is
consistent.

<Warning>
A manifest-declared plugin that is incompatible with the new core — or otherwise
cannot load — **aborts boot loudly**: the process exits naming the module, its
kind, and the reason, rather than coming up missing a plugin the manifest asked
for. Fix or update the plugin, point the manifest at a working one, or remove it
from the manifest, then boot again. A plugin that cannot load during a live
config reload aborts that reload instead: the previous generation keeps serving
and the reload call returns the failure (a non-2xx naming the module, which `tai
config reload` prints before exiting non-zero). Keep the plugin prefix on
persistent storage so the installed set survives the container recreation an
upgrade performs.
</Warning>
