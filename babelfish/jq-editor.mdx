Every jq expression a flow carries — a node's expression, a branch or loop
condition, a binding's injection or update jq — is authored in one field two ways:
as jq text, or on the canvas of the platform's [built-in jq editor](/studio/jq-editor),
the same editor every Studio jq field uses.

<Note>
This page covers what is specific to authoring a **flow**: the field's tabs and what
each field seeds the editor with.
</Note>

## Inline or Template

A jq field in the flow editor is a two-tab control — **Inline** and **Template** —
and the two are mutually exclusive: the wire carries exactly one.

- **Inline** is jq-studio's [`JqField`](/studio/jq-editor#the-field).
- **Template** picks a stored [template](/concepts/storage-and-resources) and edits
  its kwargs through a schema-assisted form.

The active tab follows the draft: a field that already holds a template opens on
**Template**, otherwise on **Inline**. There is no separate "Editor" tab and no
auto-open of the canvas. Switching tabs is a mode change that clears the mode
you leave, after a confirm when it holds data.

The editor's [non-destructive fallback](/studio/jq-editor#the-canvas) for an expression
it cannot draw lives inside the dialog; it is not a tab.

## What each field seeds

Every jq field follows one rule for what it reads: **`.` holds only the data the
expression is about, and everything the platform adds beside it — the state
documents, the run identity, the loop context — arrives as a named jq variable**
([the platform-wide rule](/concepts/jq-variables)). So each field names what `.` is
at its site, and the editor's **Test** panel seeds a sample of that shape plus a
skeleton for each variable the site binds; where the engine exposes a matching
validator, the **Validate** action checks the same shape server-side:

- a node **expression** and a **conditional** or **branch** condition see the **node
  envelope** — the run's inputs and the upstream nodes' outputs, with this node's
  `.result` still null (a condition must return true or false);
- an **On Error** condition or expression sees the **error envelope** — the failed
  node's error on `.upstream_outputs` (`.error`, `.error_type`, `.error_kind`,
  `.additional`); there `.upstream_outputs.<node>` is that node's output history (a
  list, newest last), so read the latest output as `.upstream_outputs.<node>[-1]`. The
  four error keys shadow a node of the same name, `.result` is null, and
  `.upstream_inputs` is null when the flow-level On Error runs on the run's terminal
  failure. A read of a field off `.upstream_outputs.<node>` in an On Error program, or
  in a Recovery node's expression where it runs as the handler, is refused at build
  however the program spells it — a dotted path, a pipe, an `as` alias, a bracket key,
  inside a string's `\(...)` interpolation. A `type == "array"` or `== null` test on the
  entry narrows the branch it guards, so the spelled-out idiom below is read as the
  latest output in both runs. A Recovery node that ordinary routing also reaches runs
  the same expression as a normal step too, where `.upstream_outputs.<node>` is the
  latest output itself; read it as
  `(.upstream_outputs.<node> | if type == "array" then .[-1] else . end)` to get the
  latest output in both runs;
- the flow-level On Error's **Reply** sees the same error envelope, with the handler's
  outcome under `.upstream_outputs.additional` (`.handler_result`, or `.handler_error` when
  the handler failed), and must return text or `null`
  ([the participant reply](/babelfish#the-participant-reply-on-a-failed-run));
- a node's **return expression** sees the narrow **return namespace** — only
  `.result`, `.outputs`, and `.flow_graph_kwargs`; here `.upstream_outputs` is a
  **hard build error**, not a null;
- a binding's **input injection** jq runs after the node's input is assembled, before the node runs: a
  template `input` program sees the **record** (`.` is the subject's document at the
  attach path) with its declared `params` bound as the single object `$params`; a
  **custom** injection reads the bound **record** as `.` with `$input` the node's
  input so far, and its value is placed into the input at the injection's `into`
  field;
- a binding's **update** jq runs after the node completes and reads the node's
  **output** as `.`: a template `update` picks a named update program and shapes its
  declared input through an **adapter** (`.` the node output, `$input` the run input),
  while a **custom** update reads `.` the node output with `$record` the bound record
  and `$input` the run input and returns the template-relative **op batch**
  (`[{op, path, value}]`), where a per-op compare-and-set guard rides an op as
  `{path, expected}`;
- an update's **op-id** jq reads the node's **output** as `.` with `$input` the run
  input, and returns the key the write dedupes on;
- a binding's **subject** and **scope** expressions see the bare **flow inputs** document
  (`.` is `flow_graph_kwargs`, no envelope; `scope_expr` must return true or false);
- a **holder** node's **Cancel**, **Resume**, **Start**, and **warm-start** jqs see the
  **node envelope** with the held target's parked interactions bound as `$parked`;
- a loop's **`while` condition** sees the **node envelope** with `$iterate` present —
  `$iterate.item` is always null there, while `$iterate.prior_outputs` holds the
  per-iteration results the condition tests;
- a loop's **`foreach` expression** and a string loop **`count`** see the **node
  envelope** — for a `foreach` driver `$iterate` is the *enclosing* loop, not this
  one; a `count` runs jq only when the count is a string (a literal number bypasses
  it);
- a **map item argument** sees the **loop-body envelope**, where `$iterate.item` is
  the current item (never null here) and `$iterate.iteration` its zero-based position.

`.outputs.<node>` and `.inputs.<node>` hold a node's results in order, newest last, for
each node some expression of the flow names there (in a return expression `.inputs` is
empty, and in a Recovery handler run it holds the tool's arguments); the run state keeps no
history of a node no expression reads that way (see [Run state](/babelfish#run-state)). A
field read off that list (`.outputs.<node>.<field>`) is refused at build; read the latest
result as `.outputs.<node>[-1].<field>`. A `type == "array"` or `== null` test on the entry
narrows the branch it guards, so `if .outputs.<node> == null then … else
.outputs.<node>[-1].<field> end` builds. A conditional's entry exists only when an On Error
handler may recover one of its branches (the branch's own, else the flow's On Error or
`FLOW_DEFAULT_ON_ERROR`); it is read the same way.

The build types every expression against the envelope of its field and refuses what jq is
proven to get wrong there whenever the value is present: a field read on a node's stored output history; a
comparison of a schema-typed field against a literal of a type or enum value it can never
equal; a field read on a list the schema declares (read `.<list>[0].<field>` for one element
or `.<list>[].<field>` for each); a number index on an object (in a node expression
`.upstream_outputs.<node>` is the output itself, so `.upstream_outputs.<node>[-1]` raises);
a number index on a string, a number or a boolean, one or several (`[0, 1]`), such as a field
the schema declares a string (jq indexes a string only by a slice: read `.<string>[0:1]`); a slice of an object, a
number or a boolean; an iteration (`[]`) of a string, a number, a boolean or a read that is
`null` wherever it runs (iterate it as `(.<read> // [])[]`);
a field read on a field the schema declares a string, a number or a boolean; and an `==` /
`!=` between a list or an object and a scalar literal, which is always false (or always
true). A read is refused only when nothing it may be other than `null` — after a `type` or
`null` test narrows it, and on the right of a `//` where the left side's read is `null` or
`false` — is a value the step can take. A `null` (an optional field left out, a node that has
not run) never saves a read: a field the schema declares a string and leaves optional refuses
`.<field>.x`, which raises on every run that stores it. A step is refused the same way inside a
`try` body or under `?`, where jq swallows its raise and yields no output: the read is wrong
there too, so write the read that holds rather than a `try` around one that fails. A comparison whose operand has a fallback that may equal
the literal (`// "x"`, `else "x"`, `catch "x"`) is never refused. Nothing is refused where
jq never runs: in a branch a literal condition never takes (the `then` of `if false` or
`if null`, the `else` of any other literal, an `elif` condition there included); in the `else`
of a condition whose every output is a number, a string, a list or an object (an array or
object construction, an interpolated string, `length`); and on the right of a
`//` whose left side always yields a value other than `null` or `false` — a literal such as
`"x"` or `1`, an array construction, an object construction or an interpolated string whose
parts all yield a value, `length`, a comma with such a side (`(.<read>, 1)`), a `//` whose
fallback is such a value (`(.<read> // "x")`), or an `if` with an `else` whose every branch is
one. After a read that may be `null`, an iteration, an `if` without `else` or an object whose
entry may yield no output (`{k: empty}`), the right of the `//` runs, so it is checked.

A node an On Error handler may recover (its own, or that of the branch that routed to it)
stores the handler's result as its output, so its `.upstream_outputs.<node>` entry, each
element of `.outputs.<node>` and its `return_expr`'s `.result` may also be that result: an
object an `expr` handler builds, or any value a handler tool returns. The schema does not
describe that result, so a read of such a node is refused only when it fails on the
handler's result too, such as comparing the output to a scalar when the handler is an `expr`.

A holder with an [ask exit](/babelfish#the-ask-exit-and-sending-an-ask-up) (`on_ask`, with
send-up off) stores `{"status": "asked", "asks": [...]}` as its output when its held call
settles with caller asks, each ask a parked entry (`.id`, `.status`, ...). So its
`.upstream_outputs.<node>` entry, each element of `.outputs.<node>` and its `return_expr`'s
`.result` may also be that object: `.upstream_outputs.<node>.asks[0].id` and
`.upstream_outputs.<node>.status == "asked"` build, and a read of such a holder is refused
only when it fails on the asked object too.

An
expression that reads `.outputs` or `.inputs` as a whole — `.outputs | keys`, `getpath(...)`,
`..`, a function over the channel — or uses a construct the engine does not analyse (an inline
`def`, `label`, destructuring) makes the flow keep every node's full history;
**Validate** reports it as a `state_read_unbounded` warning naming the expression, and the
flow still saves and runs. At run time each expression receives only the `.outputs` /
`.inputs` entries it names (a channel it reads as a whole, it receives whole), so its result
is the same, and its evaluation's trace record shows just those entries.

A wired **Recovery** node's expression also runs when an On Error dispatches it: there it
reads the error envelope's `.upstream_outputs` (each node's history list plus the error
keys) and `.outputs`, and its `.inputs` is the handler's keyword arguments — the Recovery
node's own baseline arguments with the On Error expression's overrides applied — not the
inputs channel. The editor notes this on that node's expression field: on a node no
ordinary routing reaches it reads *This node runs only as the On Error handler*, and on a
node ordinary routing also reaches, *At a recovery target this expr also runs as the On
Error handler*.

The engine checks that expression in each envelope it runs in. On a node no ordinary routing
reaches it is checked only in the error envelope, so a read of an error key such as
`.upstream_outputs.error` builds. On a node ordinary routing also reaches it is checked in the
node envelope too, where an `.upstream_outputs` key must name an upstream node, so the same read
is a build error. Validation likewise reports a `state_read_unbounded` warning for each
envelope in which the expression's reads cannot be bounded.

## The variables beside the input

Beside `.`, every flow jq binds the run's context as named variables, reachable
anywhere in the expression — inside a `map(...)` or `select(...)` too, where `.` is
rebound. The editor lists them on each field and seeds a sample for each in the Test
panel:

| Variable | What it holds |
| --- | --- |
| `$states` | The run's committed state documents, read as `$states.<name>.<field>`; null on a stateless run. |
| `$run` | The current run's identity — `$run.id` the session id, `$run.epoch` the state-mint epoch (null before one is sealed). |
| `$iteration` | The enclosing loop's zero-based position (0 outside a loop). |
| `$iterate` | The enclosing loop context, or null outside a loop; inside a body `$iterate.item` is the current item and `$iterate.iteration` its position. |
| `$attachments` | The attachment envelope the template `attachment(...)` locator reads. |
| `$current_user` | The calling user's id, or null for an anonymous caller. |

An **On Error** condition, expression and Reply — and a Recovery node's expression when the
On Error dispatches it — bind `$states`, `$run`, `$attachments` and `$current_user` as
above, while `$iterate` is null and `$iteration` 0 there, even when the failure happened
inside a loop body.

A **holder** node's start, cancel, resume and warm-start jqs add `$parked` — the
parked interactions on the held target, a list of `{id, status, …}` (status `asking`,
`running`, `finished`, or `failed`). A **state-binding** jq adds `$input` (the run
input) and, on a custom update, `$record` (the subject's committed record). A read of
an **undeclared** variable is a compile-time refusal at save, never a silent null. A
call to a template jq (`tjq_<name>({…})`) is checked at save against the templates
attached to the flow's bound states where the flow is validated by name (the editor's
save, a route bind), and admitted on a preset write, which carries no environment; a
run where the template is not attached refuses it loudly. The names the platform binds
cannot be rebound with `... as $name`.

## Autocomplete from a state's template jq

A jq field that can reach a bound state offers autocomplete from the
[template jq](/babelfish#state-templates) of the templates attached to that state.
Typing offers each `purpose: "input"` template jq by name and inserts its call
handle — `tjq_<name>({…})`, or `tjq_<template>__<name>({…})` when a name is
shared across the state's attachments — so an expression reads a template's value
through the prelude without hand-writing the def. The suggestions come from the
served [state-template document](/babelfish#state-templates)'s `template_jq` for the
bound state's templates, so they track whatever the attachment declares.
