Babelfish is TAI42's paid product family for teams that need agent work to run
deterministically in production. It is built on the same open platform this site
documents, and it reaches a running server the same way any other plugin does.

<Note>
Babelfish is proprietary and licensed commercially — it is not part of the
Apache-2.0 platform and is not published to PyPI or listed in the
[marketplace](/concepts/marketplace). Product details and pricing live at
[tai42.ai/babelfish](https://tai42.ai/babelfish).
</Note>

## What it adds

Babelfish Flows ships as one installable plugin carrying two halves:

- **A flow engine.** Deterministic flows registered as ordinary
  [tools](/concepts/tools-and-extensions) through the public contract — run a
  flow, step it, read its state, and abort it. Because they are tools, everything
  the platform already does to a tool applies: access control, backends,
  schedules, and tracing.
- **A flow editor in the Studio.** A front-end bundle the runtime serves to the
  [Studio](/studio) through its integrity-pinned import map, contributing a
  top-level **Babelfish Flows** page and its sidebar entry; the states a flow binds
  live on the platform [States screen](/studio/screens#states). On the canvas, nodes can be gathered
  into named, collapsible groups — a collapsed group renders as one card that hides
  its members and reroutes their boundary edges, and expanding it reveals them
  again. Groups persist with the flow and carry across the editable, run,
  read-only history, and reading views, showing an aggregated member status in Run
  mode; the collapse/expand toggle itself is a transient view preference and is not
  saved.

A saved flow is a versioned [preset](/concepts/presets) with the graph carried in
the preset's fixed arguments, so flows version, diff, and roll back through the
[versioning spine](/concepts/versioning-spine) like everything else.

## The explanation layer

A flow carries an explanation layer aimed at the person reading it, not just the
engine running it. Nodes and flows take plain-language descriptions, the editor
renders a generated legend that summarizes what a flow does and the pieces it uses,
and a dedicated reading view presents the whole flow as an annotated walkthrough — a
calm, non-editable mode for reviewing or explaining a flow without changing it.

## Presets

Beyond the built-in steps, you can define your own palette nodes from saved flows:
promote a flow into a reusable node, give it a category and an icon, and it appears
in the editor's palette alongside the defaults for anyone to drop into a new flow.

Babelfish ships two ready-made interaction nodes to start from — **send** and
**ask** — one full surface each, covering the common conversation moves out of the
box. **Send** delivers one-way and **never waits**: a text message, display
**media** (a list of `{kind: image | link, url, caption?}` items), tappable
**options**, a pre-approved **template**, or a fillable form **schema** delivering
a schema-rendered [ask-less form](/concepts/notifications#ask-less-forms) — the
outcome is `sent` or `failed`, and a form's submission, if it comes, arrives as the
person's next message on the conversation route. Its face opens on a **kind**
selector — message, media, options, template, or form — that guides the fields
while the node stays one delivery whatever the face: `kind` is face-only and never
delivered, every send carries a message or media, and one message carries one
interactive surface (a template stands alone). **Ask** pauses for a person's reply
and **always waits**, re-asking until the answer is valid or the attempts run out;
its **format** selects how the answer is collected — `text` (free text, with
optional `options` as tap-to-send suggested replies), `confirm` (a yes/no —
declining is an answer), `select` (one pick from `options`), `form` (an answer
validated against `schema`), or `external` (an action completed on a surface
reached through `link`, with the callback payload as the answer) — and the same
format drives the face's variant picker. A `form` ask also takes two per-send extras
layered over the schema for ONE send — the same
[`data` and `pages`](/concepts/interactions#prefilling-per-send-options-and-pages)
the platform's ask surface carries: `data.values` prefills top-level properties (each
shown filled in and validated), `data.options` supplies a per-send choice list that
replaces a string property's `enum` for this send, and `pages` splits the form into
ordered titled steps (every property appearing exactly once; absent `pages` is one
page). Both forward to the ask door only when set, validated against the form's schema. Both nodes take optional display media
beside their prompt, every optional field is inert when omitted, and field
combinations richer than any single face stay expressible through each node's
full-surface **Anything** face.

**Addressing is pre-wired to the conversation.** A freshly dropped send or ask node
opens already addressed to the same channel and counterpart the flow's conversation
runs on — so one flow works across every channel and always reaches the person of the
current conversation. The wiring is a **visible, editable jq expression** seeded into
the node's addressing slot (through the [visual jq editor](#the-visual-jq-editor)),
never a hidden default: it reads the guest's own `{channel, sender}` off the
conversation-routed flow's inputs, and the node's own literal addressing merges under
it. Off a conversation route those inputs are absent, and the expression is written to
drop its empty values, so it **contributes nothing** — the node falls back to whatever
you address it to by hand. A reply that rides the route itself needs no addressing at
all.

A conversation-routed flow also reads **`.flow_graph_kwargs.turn`** — the turn the
inbound entered as, surfaced on every conversation turn as `{id, inbound: {id, kind,
source}}`. `turn.id` is the turn's stable id (the answer record's id); `turn.inbound`
describes the entry — `inbound.kind` is `"message"` or `"event"`, `inbound.id` is the
channel provider message id, the event id, or the api record id, and `inbound.source`
is the channel name, `event:<kind>`, or `api`. An [event
turn](/reference/conversation-bridge#the-event-door) additionally carries
`.flow_graph_kwargs.event` (`{id, kind, payload}`) with `.flow_graph_kwargs.message`
and `.sender` both `null`. These arrive under `flow_graph_kwargs` because the
conversation route's default no-`payload_expr` kwargs are `{message, sender, turn}`
(plus `event` on an event turn); a route with its own `payload_expr` reads `.turn` and
`.event` on the payload and forwards what it wants. A conversation-target flow preset
must not declare `additionalProperties: false` without admitting `turn` (and `event`)
in its input schema, or the routing that validates the kwargs against the preset's
input schema refuses them.

A preset is a saved flow published to the palette, and it is managed **as a
node, not as a flow**. The palette's Presets section gives each card an edit
control that opens its flow editor and a delete control that raises a guarded
confirm, and a **+ New preset** action starts a fresh one in place. Deletion
routes through ordinary [preset](/concepts/presets) deletion, so it unregisters the
tool; the confirm states the blast radius plainly — the node leaves the palette, and
any flow that already embeds it keeps a now-dangling reference to it. A preset
lives in the palette **only**: the flows list shows flows, never presets — nor a
category folder emptied by them — so a palette-managed node never surfaces among your
standalone flows.

## Looping over a list

The **map** node is a first-class "friendly foreach": it runs one tool over a list.
Its face is a list `input` (a jq expression producing the items), the mapped tool,
per-item keyword arguments (jq expressions that may read the current item and its
zero-based index through `.iterate.item` and `.iterate.iteration`), and the
producer nodes whose outputs those expressions may read. It runs either
`sequential` or `parallel`, with an optional concurrency cap on the parallel mode,
and an optional `collect` expression that shapes the mapped results — left unset,
downstream reads the raw per-item output list directly.

A map compiles down to the engine's ordinary loop primitive: on save it becomes one
loop node plus one body, and on load that marked cluster folds back into the single
map node, so you never touch the mechanism. A loop authored by hand carries no such
marker, is never folded into a map, and stays a visible Loop.

Because a map *is* a loop on the wire, its entry is a barrier: the map face carries
the same dispatch controls a hand-authored loop does — the [wait mode and the
give-up pair](#node-waits), and the opt-in [state refresh](#refresh-opt-in-state-re-read),
which fires **once at loop entry** so every iteration inherits the same fresh view.

**Broadcast** is the map-plus-send recipe for fanning one message out to N
recipients: make the mapped tool the **send** node, set `input` to the
recipients list, and read the current recipient from `.iterate.item` in the
per-item arguments. The per-item output list is the delivery transcript — one slot
per recipient, in order — and because send recovers a failed delivery into
a `failed` outcome in-body, a partial failure simply appears as failed slots in that
transcript rather than aborting the whole map. Scale a large list with the parallel
mode and a concurrency cap, and shape a sent/failed summary with `collect`.

## Inputs and results

Each flow declares its own inputs and results — the values it expects when it starts
and the values it hands back when it finishes — so a flow presents a clear contract
to whatever calls it and the editor can prompt for the right inputs when you run one.
Because a flow is a [tool](/concepts/tools-and-extensions), a parent flow can invoke
another flow as a subflow through that same contract.

A subflow also **joins the dispatching run's trace** rather than minting a separate
one, and so does an agent a node drives — see [one run, one
trace](/operate/observe#one-run-one-trace). The join survives parking, including a
completing child cascading into its parked parent.

Every jq input also carries **`.run`** — the executor's identity for the run the
expression evaluates in — as `{id, epoch}`. `.run.id` is the run's session id (the
run registry key), so a flow-as-tool subflow reads a **distinct** `.run.id` from its
parent — the sub-run's own id. `.run.epoch` is the state-mint epoch, `null` on a
stateless run and until the run's stateful mint has run. Outside a run — a
validation-time compile — `.run` is `null`.

<Warning>
A subflow's state writes are invisible to a later parent node unless that node opts
in. A run's `.states` view is its snapshot from run start plus its own fills: a
subflow's fills land on the shared record immediately, but a later parent node folds
them in only if it sets [refresh state](#refresh-opt-in-state-re-read). Without it the
parent keeps reading its mint-time snapshot — a silent stale read.

A subflow reads only the states **it** is bound to, fresh at its own start; an
unbound `.states.<name>` reads as **null** — bind it, or the `state_unbound` lint
flags it. The lint runs per subflow against **that subflow's own** bindings — a state
the parent binds never masks a read the subflow makes unbound — and its findings carry
the subflow's path into the Studio problems panel like the parent's.
</Warning>

## Portable flow files

A flow exports to a single `.babelfish-flow.json` file — the stored graph verbatim —
and imports back the same way. When the flow carries state bindings, the export gains
an optional **`state_bindings` sidecar**: each binding travels alongside the graph
with its state name, its subject expression and fills (guards included), and a stable
**schema fingerprint** of the state's declaration at export time. The graph itself is
untouched and the sidecar is never persisted onto the saved preset, so a flow with no
bindings exports byte-identically to the pre-sidecar format and an older file (no
sidecar) imports exactly as before.

On import, the editor offers to re-attach each carried binding against the target
environment's states. A state of that name whose schema fingerprint still matches
re-attaches straight through; when the schema has changed, each bound path is
re-checked and the binding re-attaches only if every path still resolves; a state
that does not exist here, or a bound path that no longer resolves, is reported per
binding and left unattached rather than silently dropped.

## Structured agent output

An agent node can be constrained to return a validated object instead of free text.
Its Settings carry a **Structured output** schema editor — a JSON Schema whose
top-level `title` is required, since the engine uses that title to name the
structured response and refuses a run it cannot produce against the schema. With a
schema set, the node's Output contract renders it live and reads **Output
(structured)**; cleared, the node returns text. The constraint is the
node's own — it shapes what the agent hands back, and downstream steps read the
validated object.

A finished run mirrors that declared shape onto the **actual** result: the value reads
against the schema rather than as a raw tree, and the mirror never hides data that
does not fit it. See [the Flows editor](/babelfish/studio#schema-aware-run-results) for the
rendered view and the guarantees it makes.

## Node waits

A fan-in node runs once its **input barrier** releases, and the barrier has three
mutually exclusive modes set on the node:

- **All inputs (the default).** The node waits for every declared or edge-derived
  input to arrive, then runs.
- **Quorum.** A minimum input count releases the node once any that many inputs
  have arrived; it is purely count-based and never looks at which inputs arrived.
- **Named release.** A named-producer list releases the node once every named
  producer is present in the fan-in — a barrier keyed on specific producers rather
  than a count. Every other input is still consumed if it happened to arrive by
  release time, but is never waited on.

Named release and quorum are **complementary and mutually exclusive**: named
answers "wait for these specific producers", quorum answers "wait for any k of
them", and setting both is rejected at validation. Each named producer must be one
of the node's inputs after edge-merge, and its unwaited incoming edges render as
**dashed, read-only** on the canvas so the optional producers are visible at a
glance.

A named producer counts as present once it produced output **somewhere in the run**
— which is not the same as that output being delivered to your node as a trigger. If
the producer sits behind a conditional whose branch routes elsewhere, its output
lands in state but nothing re-invokes your node, the barrier is never re-evaluated,
and the node simply does not run (the run goes quiescent and completes as success).
When a behind-a-condition producer might route away from you, pair the named release
with a **wait timeout** so a later trigger can force a partial run.

**The give-up pair.** A wait carries an optional **wait timeout** and a
**raise-on-timeout** flag, and the pair is the barrier's safety valve on any fan-in
node — and on an **iterate** (or its **map** face), whose loop entry is itself an
all-or-nothing barrier. Left to force-run (the default), a trigger arriving after the
deadline releases the barrier with whatever inputs are present and the node runs a
partial; set raise-on-timeout and that same lapsed deadline instead **fails the node
loudly**, attributed to the waiting node as an *application* error rather than
infrastructure — so a flow-level on-error handler sees it exactly as any node
failure and can route on it. The timeout is lazy either way: it
can only fire when some trigger arrives after the deadline, so a node whose last
trigger already fired keeps waiting forever. Because the wait's start clock is
checkpointed, size the timeout against wall-clock park durations — a long upstream
park can make the first trigger after a resume find the deadline already elapsed and
force the give-up immediately.

## Handling a node's error

A node — and a conditional branch, and the flow itself — can carry an **on-error
handler**. When the node fails, the handler runs, its result becomes the failed
node's output, and the run continues from there rather than aborting.

A handler's jq reads the failure through `.upstream_outputs`, the same namespace
predecessor outputs use, alongside the ordinary run channels:

| jq path | What it holds |
| --- | --- |
| `.upstream_outputs.error` | The exception payload as raised — a dict is carried verbatim so jq can navigate it (`.upstream_outputs.error.code == 404`), anything else is its string form. |
| `.upstream_outputs.error_type` | The exception class name, for gating on a specific type. |
| `.upstream_outputs.error_kind` | The platform's stable error label. It survives class renames, so it is the durable key to route on. |
| `.inputs` / `.outputs` | The failed node's inputs, and the run's outputs at failure. |
| `.states` / `.flow_graph_kwargs` | Declared state and the run's own inputs, exactly as any other authored jq reads them. |

There are two ways to dispatch a handler, and they are exclusive — declaring both
is refused rather than silently preferring one:

- **A wired handler node.** Name another runnable in the flow. It is dispatched only
  through the error-recovery seam.
- **An inline handler tool.** Attach a **tool** directly to On Error, with optional
  baseline keyword arguments that the handler's expression overrides map onto. Any
  registered tool qualifies — including a flow-call preset, which makes the handler
  an arbitrary **nested flow**.

A handler may also be a bare expression that shapes a recovery value without
dispatching anything. Baseline kwargs without a tool to receive them are refused, and
a handler with no tool, node, or expression at all is refused as inert.

<Warning>
A **recovery-only** handler node — one no ordinary routing reaches — never runs as a
live graph step, so an edge **out** of it can never fire and an `inputs` reference
**to** it reads an output that is never written. Both leave a downstream node waiting
on its barrier forever, so both are rejected as dead wires. Wire the handler into the
flow's ordinary routing if you need its output downstream.
</Warning>

Validation also **warns** when a wired handler has no incoming routing and the flow
declares no entry points: the builder auto-promotes every unrouted node to a start
entry, so that handler would run unconditionally at flow start *as well as* on error.
Wire an incoming edge to it, or declare the flow's entry points explicitly, to keep it
handler-only.

**A flow-level handler is a different job.** A handler attached to the flow itself —
the Start-attached one — runs only on the terminal error path, and the run still
**fails**. It decorates the failure: it can send a notification or shape the error
that surfaces, but it cannot rescue the run.

To recover from a failure and keep running, put the handler on the failing node
instead. The editor names which of the two you are editing on the form itself, so
the rescuing kind and the decorating kind are never confused.

A finished run shows what the handler did. A node that failed and was rescued reads
as recovered, and the handler that ran — whether the On Error attachment or the wired
target — reads as having run through the recovery path rather than as an ordinary
step. A node reached both ways keeps its own status and gains the handler mark.

## Run condition

Any scheduled node — a runnable, an agent, a flow call, a map, and a router's
classifier — can carry an optional **run condition**: a jq predicate authored as an
inline expression or a stored template with kwargs (the same field triple every jq
site uses), answering one question — *should this node run at all?* Left empty, the
node is unconditional and runs exactly as it did before the feature existed.

The condition is evaluated at fire time — after the node's input barrier releases and
after its [state refresh](#refresh-opt-in-state-re-read), before the node does any work
of its own, including its own expression — over the same namespace that node's
expression reads. It is **bool-strict**, like a conditional's condition: anything but
`true` or `false` is an authoring defect, and a condition that raises fails the node
down its normal error path. It is statically checked like every other jq slot, so an
unresolvable upstream read or a schema-impossible comparison is a build error.

- **True** runs the node normally.
- **False** *skips* it: the node does not execute, its output is `null`, and its status
  reads **skipped**. The output key is still written, so every downstream input barrier
  still releases and the flow **continues past** the node — the gate stops the one node,
  not the path. To stop a whole path, use a conditional or a router instead.

A skip is not a failure, so a skipped node never reaches its own [on-error
handler](#handling-a-nodes-error) — the skip happens before any execution that could
fail — and it **settles** the node, so a re-drive of the run re-evaluates nothing. A
node flagged to return a result still contributes its key when skipped, with the value
`null`, so a return expression on a node you might skip must tolerate a null input.

The gate belongs on a **scheduled** node. A node that runs only as an [on-error
handler](#handling-a-nodes-error) is dispatched directly and never scheduled, so a
condition on it would never be evaluated; the editor does not offer the field there —
unless one is already stored, in which case it renders with that fact stated, so the
dead value is visible and clearable rather than silently kept.

<Note>
A node whose tool pauses and resumes re-runs its whole node function on resume, so its
run condition is evaluated **again** over the resume-time view — one a peer may have
moved during the pause. A condition that answered true on the first drive and false on
the resume drive reports the node skipped with a null output even though the tool
already ran. This is inherent to interrupt-resume re-execution: a condition over values
that can change while the node waits carries the edge, one over the node's settled
fan-in does not.
</Note>

## Routing with an LLM

A **router** node classifies its input with an LLM and routes on the result — one
card instead of an agent node wired into a hand-built conditional. You declare the
**kinds** it may classify into, each with a name and a description, and the node
generates the structured-output schema and appends the kinds to your prompt, so the
classification and the routing can never drift apart. A kind may carry extra
per-kind fields, merged into each extracted item beside its text.

Three kinds of edge leave the card, each drawn distinctly:

- **Kind** — fires when the classifier produced that kind. An optional jq guard is
  combined with it, so "this kind, but only when…" stays one edge.
- **Condition** — the branch condition *is* an authored jq expression with full
  access to the run, `.states` included. It is a condition route, not a disguised
  kind, and the canvas says so.
- **Otherwise** — the default branch, taken when no other branch matched.

Several branches may share one target, and a declared kind that is not wired is
still classified — it stays in the generated schema and in the model's output, it
just routes nowhere.

Renaming a kind re-keys its branch, its schema property, and its prompt bullet
together, so every wired edge survives the rename untouched. On save the card lowers
to ordinary engine parts — one agent call plus one hidden conditional — and folds
back into the single card on load, the same way a [map](#looping-over-a-list) folds.
A conditional you author by hand carries no such marker and stays a visible decision.

### Every match or first match

A router's routes fire under one of two **dispatch** disciplines, set on the card:

- **Every match (the default).** Every route whose condition holds fires, in parallel
  — the multi-fire fan-out. This is the discipline every router has always run under,
  and it carries no wire marker: a router that never touched the mode is byte-identical
  to before the setting existed.
- **First match.** The routes are evaluated in **row order** and only the **first** one
  that matches fires; the rest are never evaluated. This is the classic single-path
  routing table — at most one route ever fires.

Because a router lowers to a hidden conditional, its dispatch *is* that conditional's
routing discipline and its routes *are* the conditional's branches: a kind route or a
when route is a predicate branch, and the single **otherwise** route is the default
branch, taken only when nothing else matched.

Under first match, row order is **semantic**, so it cannot ride the member order of a
JSON object — object member order is not meaningful and does not survive every store a
flow passes through (Postgres `jsonb`, for one, re-keys members by key length then
bytewise). The order instead rides an explicit **array** of route keys that no store can
permute, written on save from the routes table below. A flow authored before that
carrier existed keeps running in whatever order it already had, and the first
arrangement made in the table pins it. The array must list every route exactly once — a
partial or unknown listing is refused at load rather than guessed at runtime.

First-match order carries two guard rails, refused loudly at load and scoped to first
match (every-match routing is order-free, so neither rule constrains it):

- **At most one catch-all, and an unconditional one comes last.** An always-true route
  makes every route below it unreachable, and a second catch-all can never fire — so
  declaring either is refused with the dead rows named. A plain **otherwise** route is
  order-free (it fires only when nothing matched, wherever it sits) and may be declared
  anywhere.
- **Route keys are never plain numbers.** A numeric branch key is an array index that a
  JSON-object client silently re-orders ahead of every other key; the router never mints
  one, and the engine refuses it whether or not an order carrier rides, so the two
  spellings of a first-match table cannot disagree.

### The routes table

Below the card, the **routes table** is one view over the router's routes: one row per
wired route, in the order they lower. Each row shows its flavor — **kind**, **when**
(the table's name for a Condition route), or **otherwise** — the kind or
when-condition, an optional per-kind **guard**, and its
**target**. Conditions and guards are edited in place; a route's target is the edge you
drew from its chip on the card, so the table **shows** it, never picks it — the canvas
stays the one place edges are drawn.

A kind row's guard is AND-composed with the pinned non-empty check for that kind, so the
route fires only when the kind matched *and* the guard holds. A when row's condition *is*
its branch condition, reading the classified output, other node outputs, and `.states`.

Under **first match** the table also **orders** the rows — the row number is the
evaluation priority. Reorder a row two ways: drag it by its grip, or step it with its
move buttons (the keyboard and assistive-technology path). The reorder is a plain array
move with no wire format of its own; targets, guards, and conditions ride along
untouched. Under the every-match default the order is only a position, so the reorder
controls are absent.

The table also carries **advisory** notes — never a block on saving — when a first-match
row is already covered by an earlier one, when a row repeats an earlier one to the same
target, or when the otherwise row sits above rows still being evaluated and so reads out
of order.

### Turn-level output fields

A router can describe not just the items it **extracts** but facts about the **whole
turn**. Beside the kinds, declare optional **turn-level output fields** — a JSON-Schema
`properties` fragment merged into the generated response format and required alongside
the kinds — so a field like `staff` or `sentiment` becomes an ordinary top-level output
read as `.upstream_outputs.<router>.staff`, typed and statically checked like any other
output rather than modelled as a kind or dug out of an item. The declaration rides the
card's marker exactly as the kinds do (the response format is regenerated on every save)
and follows the same absent-key discipline as dispatch: declare none and the router is
byte-identical on the wire. Because a turn field and a kind are siblings in one output
namespace, a turn field named after a kind — which would shadow that kind's array — is
refused.

### Loop mode

A router can instead run as a **bounded loop** over the open intents a [mounted state
module](#state-modules) tracks. One card becomes the whole loop: the classifier runs
once over the inbound, then the engine iterates — each pass firing the handler of every
intent phase currently **due** — until nothing is due or a pass cap is hit. With loop
mode on the card stops being author-drawn: its kinds and its routes are **generated**
from the module's manifest, one branch per phase, and the routes table is read-only.

**The contract it needs.** Loop mode binds to a **state** this flow is bound to and a
**module** mounted on it whose document declares a [`loop` contract](#the-loop-contract).
The card reads that block for everything it lowers: the shipped preset names (`mint?`,
`seed`, `record`, `outcome`), the view role map (`anything_due(run)`,
`due(kind; phase; run)`, `due_set(run)`, `expectations(run)` — it always emits the
module's mapped view *name*, never the role name), and the manifest paths (`intents`,
`phases`, and the optional `talk_slot`) into the mount's **declarations**. Nothing here
is read from a running flow: the kinds come from the manifest's intents, one phase branch
comes from each manifest phase, and each phase's handler tool name is its `handler`
column. The card reads that snapshot from the mounted module's document and the mount's
declaration values, never from live state.

**What it lowers to.** On save the card expands to one cluster, every node marked so it
folds back to the single card on load:

- `<name>__mint` *(optional)* — the module's `mint` preset, opening the run: it mounts
  the subject and hands the classifier the open expectations and the spans left to
  classify. Omitted when the contract names no mint, and the classifier then runs
  unconditionally over the inbound.
- `<name>` — the classifier itself, run once per inbound, gated (when a mint exists) on
  the mint leaving spans to classify.
- `<name>__record` — the module's `record` preset, behind an all-inputs barrier over the
  mint and the classifier, so it releases whether the classifier ran or was skipped.
- `<name>__loop` — the engine [`iterate`](#looping-over-a-list) (`do_while: true`) whose
  body entry is the seed and whose stop condition is the contract's `anything_due` view.
  It refreshes the bound state **once at loop entry**, so the rows the mint and record
  wrote — each its own store-committing sub-run — are visible to the first pass.
- `<name>__seed` — the body entry, the module's `seed` preset: each pass writes the
  follow-ons that pass makes due.
- `<name>__router` — the hidden conditional (`dispatch: all`, refreshing state each pass),
  one branch per manifest phase.
- per phase, `<name>__h_<kind>_<phase>` → `<name>__o_<kind>_<phase>` — the handler fan-out
  and the outcome recorder (below). The id encodes the phase identity `(kind, key)`, so two
  kinds sharing a phase key stay distinct nodes; because `_` is legal in both segments the
  encoding is not injective, and the save gate blocks (and the serializer throws) on a pair
  that would collide, naming both phases.

**The generated stop and branch conditions.** Authors never write these. The loop's
`while_cond` and each branch's condition are compiled from the mapped views, with the
state, module, kind, and phase emitted as JSON string literals rather than raw
interpolation:

```text
# while_cond on <name>__loop
(.flow_graph_kwargs.turn.id) as $run | mount("journey"; "planner") | planner_has_open($run)

# one branch on <name>__router — kind "alpha", phase "gather"
(.flow_graph_kwargs.turn.id) as $run | mount("journey"; "planner") | planner_is_due("alpha"; "gather"; $run)
```

The `$run` a view reads is the [turn id](/operate/observe#one-run-one-trace); the "not
already settled this run" exclusion the routing needs lives **inside** the module's `due`
view, so the card owes nothing beyond passing `$run`.

**Handlers are fixed tool names.** Each phase branch calls the manifest's `handler` as a
plain runnable `tool` — a fixed name written into the flow JSON and validated at bind like
every node's tool, never read from state at run time. Change a handler (or any consumed
manifest field) and the card is stale: the lowering stamps a **manifest hash** on the loop
node, the save gate recomputes it from the current mount declarations, and on a mismatch
the card blocks with a *regenerate from manifest* lint. Regenerating re-derives the kinds
and phase branches from the manifest and clears it. A handler naming a tool that no longer
exists is linted in the Studio and refused at bind.

**Per-item fan-out.** A phase branch is itself a parallel foreach over the due items of
that kind and phase, calling the handler **once per item** — so a kind with three open
intents fires three handler calls in one pass. A kind outside any sequence group fans out
under the engine's default concurrency; a kind in a **sequence group** pins
`max_concurrency: 1`, firing its items one at a time in the view's rank order. The foreach
reads its items through the `due_set` view.

**The outcome recorder.** After each phase's fan-out, `<name>__o_<kind>_<phase>` calls the
module's `outcome` preset. The foreach hands it a terminal aggregate — a list, in item
order, of per-item wrappers `{"<name>__h_<kind>_<phase>__item": {status, value}}` — and the
recorder **unwraps** it to the bare list of `ok` outcomes the preset is typed for. Each
`value` is the handler's **run envelope**, so the lowering reads through it the same way it
reads every loop preset: the loop contract is that a preset returns its value under exactly
one `return_result` node, so the bare value is the sole member of `result`, read as
`.result | [.[]] | first`. The outcome node also **refreshes** the bound state after the preset
commits the pass's rows, so `anything_due` sees them at the next `while_cond` instead of
the loop over-running an empty pass. The handler tool never touches state itself; the
outcome preset's mount-materialized fill writes the ledger rows, so every state write stays
on a shipped preset.

**The classifier in loop mode.** The forced response schema gains a required `bindings`
array beside the per-kind arrays: one verdict per input span the model reads as
**answering** (or as **ambiguous** against) an open expectation, each
`{relation, target, text}` with the expectation's key as `target` (an ambiguous span lists
its candidate keys). A span that opens a *new* intent stays in that kind's array. The
classifier's run-time inputs ride **accepted agent kwargs** (never bare ones the agent
would reject): the spans to classify go through `user_message`, and the open expectations
ride `system_message_kwargs` so the expectations block's `{{ expectations | tojson }}` slot
renders them into the system message — both read off the mint through the same envelope
unwrap. The classifier reads only each item's `key`, `expected_input`, and optional
`question`; the `kind`, `fields`, and answering-party `who` the same items carry are for
compose and the re-entry match, not the prompt. When the manifest sets `talk_slot`, the schema also gains
an optional `talk` string — free text the model wants said beside the outcomes — which the
module's `record` preset stores and compose speaks last.

**The pass cap.** `max_iterations` resolves in order: the card's own override, else the
module's `loop.max_iterations`, else the platform default of **20**. Because a sequence
group spends one pass per intent, the cap must cover the longest sequence. Reaching the
cap is a **bug, not a conversation state**: the loop raises, and the failure travels the
flow's ordinary [`on_error`](#handling-a-nodes-error) path — never a settle branch. The
form computes the manifest's **longest chain** — the longest run of dependent phases one
record can produce, a minted follow-on starting a fresh count rather than extending the run —
and stores it on the card, so a save whose resolved cap is below it
is refused before it lands with *"Max passes N is below the manifest's longest chain (M
passes)."*; the canvas node's errors card shows *"Max passes below the manifest's longest
chain."*.

**No parking ask in the loop.** A handler must not be an `ask` (or any interactive)
preset: a parking ask inside a fan-out re-runs its siblings on resume, so the card lints
one out of the loop body. Loop mode also forces `dispatch: all` — a first-match discipline
would starve the other phases — and refuses an `otherwise` route, which would fire every
pass and never let the loop settle.

The contract's own shape is defined with the [module document](#the-loop-contract); loop
mode is one consumer of it, and any module that declares a `loop` block can drive it.

## The visual jq editor

Every jq expression a flow carries — a node's expression, a branch or loop
condition, a state fill or its guard — is authored in one field two ways: by typing
jq into the field's resting text control, or in a **visual editor**, opened from that
control, that draws the expression as a small, editable node graph and writes it back
as jq. The wire always carries the jq text.

<Note>
This visual editor is [**jq-studio**](/studio/jq-editor) — the platform's
open-source, built-in jq editor. The [Studio SDK](/reference/studio-sdk/index)
re-exports its `JqField` component and the Studio host provides the design system and
evaluation worker, so the flow editor renders it directly, with nothing to install.
The **same** editor serves every jq field across the Studio — a flow's, a host
feature's, another plugin's — so the canvas below is identical everywhere. See
[Visual jq in flows](/babelfish/jq-editor) for the flow field's tabs and per-surface
seeding.
</Note>

**The node vocabulary.** The canvas paints eight node kinds, each with a semantic
hue shared with the flow canvas so a colour means the same thing in both editors:

- **Input** (primary) — the data the expression receives, `.`.
- **Value** (muted) — a literal or a path into the input.
- **Operator** (muted) — combines two values (`+`, `==`, `//`, …).
- **Condition** (warning) — chooses a result with if / else.
- **Try/Catch** (danger) — runs logic and recovers on error.
- **Call Function** (primary) — applies a built-in or defined function.
- **Define Function** (primary) — declares a reusable function.
- **Comment** (muted) — a note; never runs.

Kinds that share a hue (Input, Call Function, and Define Function on primary;
Value, Operator, and Comment on muted) wear a terse kind badge and are further
told apart by glyph and shape, so two same-coloured cards never read alike. A
**Legend** on the toolbar lists every kind and the wire notations — pipe, operand,
and function grant — generated from the same registry the canvas paints from, so it
can never drift from what you see.

**The editor shell.** Around the canvas sits a **Test** panel that runs the
generated jq against sample JSON — seeded per surface with a skeleton of the right
input shape, editable, and run locally in WASM (Cmd/Ctrl+Enter) — plus, where the
engine exposes a matching validator, a **Validate** action that checks the
expression server-side. A **live readout** shows the jq the graph currently
serialises to as you edit, and an **error summary** chip counts the graph's problems
and jumps the view to each one in turn.

**The faithfulness guarantee.** The editor draws a graph only when it can prove that
reading the graph back gives exactly your expression. Before any loaded expression
is adopted for editing, its graph is serialised back to jq and a WASM oracle checks
that the two behave identically; only a faithful round-trip is drawn. Everything else
is non-destructive: an expression the editor cannot draw, or one whose graph would
read back differently, keeps your text verbatim and shows it as text with a neutral
**"not shown here"** notice — your expression is never altered, and the editable
canvas is reached only through an explicit **Start empty** that you choose. This
keeps two questions apart — *is the jq valid* and *can the editor draw it*. Only jq
that genuinely fails to compile raises a loud **"invalid expression"** alert; valid
jq the editor cannot represent is neutral, never flagged as broken.

**Where you open it.** In a flow field, the visual editor opens from the **Inline**
tab's **Visual editor** button — the field is a two-tab Inline/Template control, and
the canvas is never a tab of its own. See [Visual jq in flows](/babelfish/jq-editor)
for the field's tabs. The same editor opens the same way on every other jq field in
the Studio.

### Visual jq on every surface

Every jq field carries the same editor, and each names what `.` is at its site so the
Test panel seeds the right sample and the server validator checks the right shape. The
per-site input shapes — the node, error, fill, and return envelopes, the loop
envelopes a `while`/`foreach`/`map` field sees, and the bare flow-inputs and
state-record documents — are listed in
[Visual jq in flows](/babelfish/jq-editor#what-each-field-seeds).

## Flow states

A flow's durable cross-run memory lives in the platform
[state store](/concepts/states): named, schema'd JSON documents, one per subject,
that every door reads and writes through one seam. The engine does not own that
store — it **binds** to it. Declaring a state, mounting a module, browsing records,
and folding subjects are platform concerns (see the [States concept](/concepts/states));
what the flow engine owns is the binding: which states a flow reads and writes, under
which subject, and which node writes which field.

- **Bind a flow to a state.** A binding connects one flow to one declared state. It
  carries a jq `subject_expr` that picks the subject, per-node **fills** — the node,
  the path it writes, the operation, and two jq expressions (one for a normal run and
  an optional one that fires only when the engine detects the node re-ran; unset means
  "same as the normal jq"; a null jq result skips the write) — and an optional
  `scope_expr`. In a run, every bound state's record is available to jq as
  `.states.<name>`, seeded once at run start.
- **Typed subjects.** A `subject_expr` resolves to a **typed** subject — `{kind, key}`
  (the conversation target comes from the door) or a full
  `{target_kind, target_name, kind, key}`. A bare-string subject is not accepted:
  a `subject_expr` resolving to a string, to `null`, or to the wrong keys is a loud
  mint-door error naming the state and the expression, for example *"subject_expr for
  state 's' must resolve to a typed subject object ({kind, key} or {target_kind,
  target_name, kind, key}); expression '.thread' resolved to '…' — a bare string
  subject is not accepted"*.
- **Ambient subjects.** Leaving `subject_expr` unset binds the **ambient** subject: the
  run takes the door's candidate for the state's `default_subject_kind` (a conversation
  turn resolves `thread` always and `person` on a multichannel target; a hook or
  schedule resolves the kind it declared). A binding with no `subject_expr` reached
  through a door that resolves no candidate of that kind is a loud mint-door error:
  *"state 's' binds the ambient subject of kind 'person' but the 'conversation' door
  resolved no 'person' candidate"*.
- **Write by path.** [Keyed list ops](#keyed-state-list-ops) and compare-and-set
  [guards](#cross-flow-state-writers) are the coordination primitives for many writers
  on one record; the platform applies every op atomically under the record's row lock.
- **Refresh.** A node can opt into a fresher view of its bound records — see
  [refresh](#refresh-opt-in-state-re-read).

Flow bindings and the flow-side `flow-views` documents register a `flows-states`
section in [backup and restore](/operate/backup-and-restore); the record data is
platform state, backed up with the store like checkpoints. Engine fills land in the
platform record's [audit trail](/concepts/states#the-audit-trail) with the writing
consumer, node, and run, and emit a state-change event into the run's
[Langfuse trace](/plugins/tai42/monitoring-langfuse).

### Reading a state a flow does not bind

The run's `.states` view carries only the states **bound** to the running flow, so a
`.states.<name>` read of a state the flow does not bind resolves to null at runtime.
The engine catches this in two stages — a warning while you author, a loud error when
it runs:

- **A warning while you author.** Flow validation reports a `.states.<name>` read of a
  state that is **not declared** (`state_ref`), or is declared but **not bound** to
  this flow (`state_unbound`), or a `refresh_states` naming an unbound state
  (`state_refresh_unbound`), as a **warning** — never a save gate. The fact is
  extra-graph and per-environment: the read is fixed by binding the state at a separate
  door, so a flow authored or imported before its states are bound in this environment
  is not blocked. The message names the read and the fix, for example: *"Node 'n':
  return_expr reads .states.x, but 'x' is a declared state that is NOT bound to this
  flow, so the read resolves to null at runtime. Bind 'x' to this flow, or read a state
  it binds. States bound to this flow are […]."*
- **A loud error when it runs.** A `refresh_states` naming a state the flow does not
  bind is a loud drift error at node execution: *"node 'n' refresh_states names state(s)
  ['x'] that are not bound to this flow; bound states are […]."* A binding whose
  `subject_expr` or ambient subject cannot resolve is likewise a loud mint-door error
  naming the state and the expression.

Binding is refused at the bind door for a state that is **not declared** (*"state 'x'
is not declared"*), for a `subject_expr` that is present but blank (*"subject_expr must
be a jq expression or omitted (ambient subject)"*), and for a `subject_expr` or
`scope_expr` that does not compile in the state's mount prelude.

### Cross-flow state writers

Because overlapping writers are allowed rather than refused, where two flows race
on the same field an optional **compare-and-set guard** opts a fill into lost-update
protection. A guard is a `{path, expected_expr}` pair: `expected_expr` is a jq over
the fill's own input, evaluated engine-side into a concrete expected value, and at
write time — **under the record's row lock** — the platform compares the record's
current value at the guarded path (a missing path reads as null) to it by strict
JSON equality. Equal, and the write applies; unequal, and that one write is
guarded-skipped while the rest of the batch still applies, observable both in the
record and in the run's state-change trace.

The idiomatic use is a **writer token**: pair a field with a companion writer field,
and have each flow guard its write of the field on the writer equalling its own
token, so under a real write race exactly the token-holder writes. The guard is
deliberately narrow — it protects against lost updates only, not multi-step
invariants, and it compares equality on exactly one path (a null expected value
means "expect the field absent or null", the first-claim case). It is a flow-engine
primitive, checked only for writes the engine performs.

### Keyed state list ops

A state field that holds a **list of objects** — vetoes, line items, participants —
can be maintained item by item without ever reading the whole list and setting it
back. Five path operations do this **atomically at write time on the live record**,
under its row lock:

- **`set_by_key`** — update or append the list item whose key field equals a given
  value. The fill's jq produces the **item** itself: a JSON object that must carry
  its own key field, so the match key can never drift from the payload. The first
  item whose key field equals that key is replaced in list order; if none matches,
  the item is appended (upsert). An absent list is created. The jq may also produce
  a **list** of complete items, applied in payload order — one op, many upserts.
- **`merge_by_key`** — patch fields on items that already exist. The fill's jq
  produces a list of **partial** items, each carrying the key field; each partial is
  shallow-merged into the first stored item with that key (`{**existing, **partial}`,
  top level only — a nested object replaces wholesale rather than deep-merging).
  Null-valued fields are dropped before merging, so `null` never deletes a field. A
  partial matching nothing is skipped: unlike `set_by_key` this **never inserts**.
- **`unset_by_key`** — the deleting dual of `merge_by_key`: remove named fields from
  items that already exist. The jq produces a list of entries, each exactly
  `{<key_field>: <key>, "fields": [<name>, …]}` — the item's identity plus the
  top-level field names to delete. An already-absent field is an idempotent no-op and
  an entry matching nothing is skipped; the key field itself may never be listed,
  since an item keeps its identity. Stray keys on an entry, a duplicate field name,
  and a duplicate entry key are all refused loudly.
- **`set_by_key_each`** — the keyed **fan-out** of the upsert, for a classifier
  envelope. The jq produces an object mapping fan-out keys to lists of complete
  items; each `(key, items)` pair applies the `set_by_key` list semantics into the
  list one level deeper, at the path plus that key. One op and one atomic apply
  replace one fill per fan-out key. A fan-out key must be a non-empty string and
  never `"-"`; a key mapping to an empty list contributes nothing.
- **`remove_by_key`** — remove the list item(s) whose key field equals a given value.
  The fill's jq produces the **key** to remove by — a single scalar, or a **list of
  scalars** (the MongoDB `$pull` + `$in` idiom) that drops every item matching *any*
  listed key across all of them, in one fill. Every matching item is dropped; zero
  matches, or an absent list, is a quiet no-op. A remove list is capped at **200
  keys**; a nested container or a duplicate key is refused loudly, while an **empty**
  list is accepted as a no-op — a jq selection that legitimately matched nothing lands
  as a traced no-op rather than raising.

Every keyed op names a `key_field` — a single **top-level** field of the item
objects — and addresses the **list** itself (for `set_by_key_each`, the object holding
the fanned lists), never a new item, so the append token `"-"` is refused: the op
decides insert-versus-replace by key, not by position. A key is a **string or
integer** only; floats, booleans, null, and containers are refused as fragile
identities, and a payload list refuses duplicate keys loudly. A list item that is not
an object, or one missing the key field, never matches (and is never an error); a
non-list already sitting at the path is a loud refusal. As with any fill, a null jq
result skips the write.

`set_by_key`, `merge_by_key`, and `unset_by_key` touch exactly **one** stored item
per supplied key — the first match. `remove_by_key` keeps its remove-**all**
semantics.

This is the race-free "update the item where key equals X" that a whole-list `set`
could not express — a whole-list write reads, edits, and sets the entire list back,
so a concurrent writer's change is lost. Applying by key under the row lock instead
makes three multi-writer patterns safe with no extra coordination:

- **Distinct keys compose.** Two flows that upsert items under different keys both
  land — exactly like list appends, which always compose.
- **Appends compose with a keyed update.** One flow appending a fresh item while
  another updates an existing one by key keeps both, whatever the commit order.
- **The same key from two flows needs a guard.** Two flows racing to write the *same*
  key each replace the whole item, last-writer-wins; where that is a genuine race,
  pair the fill with a [compare-and-set guard](#cross-flow-state-writers) (the
  writer-token pattern).

A **key change** is expressed as `remove_by_key(old)` followed by `set_by_key(new)`
in the **same binding** — one node's fills, one batch, one transaction. In the
Studio, the fills editor offers every keyed op beside `set` / `remove`, captures the
key field, and captions each fill per op; a run's state-change story renders a keyed
write as `set /items where id = a` or `removed /items where id = a`.

<Note>
**Downgrade note.** Drain any keyed-fill runs before rolling a server *back* to a
build that predates keyed ops: an older server would replay a stored keyed fill as a
whole-list `set` and silently clobber the list. The forward direction is safe — a
pre-keyed binding never carries a keyed op, and an unknown op fails loud by design.
</Note>

### Refresh: opt-in state re-read

Every run seeds its bound records into `.states.<name>` **once, at mint** — so a node
reads whatever was persisted when the run started. A node can opt into a fresher view:
set **refresh state** on it to re-read the persisted record(s) right after its input
barrier releases and **before** its jq input is built, folding the freshly committed
docs into `.states.<name>` for that node's own expressions *and* its fills. Refresh
re-reads **every** state the flow binds, or you narrow it to a named subset.

The node's own control has three states:

| Node setting | Effect |
| --- | --- |
| *unset* | Inherit the flow's default. |
| *off* | Never refresh — an explicit per-node off-switch that **beats** a flow default. |
| *on* (or a named subset) | Re-read every bound state, or just the named ones. |

A flow sets `refresh_states_default` once and every node that leaves its own control
unset inherits it, so a flow whose nodes should all read fresh does not repeat the
setting on each card. A node that sets its own value always wins — including the
explicit off, which is why the control is three-state: "off" and "not configured"
are different answers once a flow default exists. With no flow default and no node
setting, a node reads the mint-time snapshot.

The default is scoped to the flow that declares it. A subflow dispatched as a tool
compiles from its own graph and resolves against its own config, so a parent's
default never crosses the flow-call boundary in either direction. A `SubFlowStart`
card therefore edits the **sub-flow's** default, and offers that sub-flow's bound
states as its subset options — never the parent's.

- **What it heals — and what it does not.** Refresh heals **causality**: a document an
  already-**finished** upstream node (or another completed flow) committed after this
  run's mint-time seed, or a fill whose channel update was rolled back at an interrupt
  boundary. A [subflow](#inputs-and-results) a parent node invokes is this case — its
  fills commit immediately but stay invisible to a later parent node until that node
  refreshes. It is **not** a race primitive — the re-read is a single point-in-time
  snapshot with no lock span, so a writer racing *concurrently* is still a
  [keyed-op](#keyed-state-list-ops) or [compare-and-set guard](#cross-flow-state-writers)
  concern, never this one. A record that reads **absent/erased** skips the landing
  entirely: a refresh cannot observe a deletion.
- **Once at loop entry.** On an **iterate** (and its **map** face) the re-read fires
  **once, at loop entry** — re-entries through the body back-edge skip the barrier — so
  every iteration's body, and any `while` predicate, inherits the same entry-time
  refreshed view.
- **Interrupt-resume caveat.** A tool node that pauses and resumes re-runs on resume, so
  its refresh re-reads at **resume** time and its fills — and the input recorded for the
  node — are recomputed over the resume-time view, which can diverge from the arguments
  the tool actually received on the first drive.
- **Stateless bypass.** On an unbound run — a raw-graph surface, or a flow imported to an
  environment where it is unbound — the re-read is a silent no-op, the same shape as
  fills. But naming, in the subset, a state the flow does **not** bind is a loud binding
  error whenever bindings do load.

In the Studio the control sits on the node's State/Settings surface beside the wait
knobs, and a refresh lands in the run's [state-change trace](#flow-states) as a
"refreshed" marker carrying no new writes.

### Enable the state store

Flow bindings read and write the platform [state store](/concepts/states), so that
store must be enabled — it defaults to the `default` database and points elsewhere
with `TAI_DB_BINDING_STATES` (see
[enabling the store](/concepts/states#enabling-the-store)). The flow engine keeps its
own small store for the bindings and the `flow-views` documents, on its own Postgres
component `flows-states`:

```bash
TAI_DB_BINDING_FLOWS_STATES=default
# plus the TAI_DATABASE_<NAME>_PG_* settings for that database
```

Then run the migrations — the plugin ships its chain under
`migrations_component: flows-states`, discovered by the shared runner:

```bash
tai db migrate
```

The boot gate refuses to serve a declared-but-unmigrated database, naming that exact
step. With the binding unset the feature is cleanly off: bound flows simply run
stateless, and the binding routes answer a gated refusal.

| Variable | Default | Effect |
| --- | --- | --- |
| `TAI_DB_BINDING_STATES` | `default` | Database the platform [state store](/concepts/states) binds to (records, declarations, modules). |
| `TAI_DB_BINDING_FLOWS_STATES` | unset | Database the flow-engine binding store binds to; unset = flow states off. |

Record retention is a platform concern now — set it per state (`retention_days`) or as
a deployment default on the store; see the [States concept](/concepts/states#enabling-the-store).

## State modules

A **state module** gives a state a *declared structure* — a reusable schema fragment,
per-path writer rules, a shared jq view library, a trace switch, a declarations section,
an optional loop contract, and shipped node presets — written in **module-relative**
names that mounting translates to concrete paths once, at bind time. It is split across
**two documents** that share a module name:

- the **platform module document** (`kind: "state-module"`) — the schema fragment, the
  fillable parameters, the per-path writer regimes, the declarations section, and the
  trace switch — owned by the platform [state store](/concepts/states#modules-and-mounts).
  Declaring it, mounting it on a state, and the effective schema the mount composes into
  are platform operations.
- the **`flow-views` document** (`kind: "flow-views"`) — the jq **views**, the
  [compiled views](#compiled-views), the optional [loop contract](#the-loop-contract),
  and the shipped **node presets** — owned by the flow engine and keyed by the same
  module name. This is the half a flow consumes.

A module is data and the runtime is generic: nothing in a module is a use-case feature —
it is a mechanism any state can reuse.

### The platform module document

The platform half is a JSON object with `kind: "state-module"`, a `name`
(`[a-z][a-z0-9-]{0,62}`; the jq identifier form maps `-` to `_`), the object-rooted
JSON-Schema `schema` fragment (a `{"$parameter": "<name>"}` marker anywhere is
substituted at mount), the `parameters` (each `{schema, default?}`), the module-relative
`regimes`, the `declarations` section (static values with their own schema and an
optional `check` predicate), and the `trace` switch. Its shape, its
[parameters and markers](/concepts/states#modules-and-mounts), the
[regimes](/concepts/states#regimes) it declares, mounting it on a state, and the
effective schema it composes into are documented with the
[platform state store](/concepts/states#modules-and-mounts); under a traced mount the
platform stamps a `_trace` object on every write.

The flow engine adds one authoring check over the served regimes at **bind time**. A
`single`-regime path admits at most one `(flow, node)` writer across every binding on the
state; a second is refused naming both — *"single-writer path […] of module 'alpha' on
state 's' admits one writer, but 'f1'/'n1' and 'f2'/'n2' both write it"*. A `composing`
path admits only [keyed ops](#keyed-state-list-ops) or an append `set` (a path ending
`'-'`); a whole-path write is refused — *"composing path […] of module 'alpha' on state
's' admits only keyed ops or an append set (path ending '-'); fill for node 'n' uses
'set'"*. The platform store additionally refuses a `composing`-shape violation at write
time, so the rule holds even for a write that never passed the bind door.

### The flow-views document

The flow-side half is a sibling document keyed by the module name, carrying only what a
flow consumes:

```jsonc
{
  "kind": "flow-views",
  "module": "alpha",
  "views": {                                // a jq library; each view's input is the mount ENVELOPE, siblings callable by relative name
    "pending":    {"expr": ".data.entries // [] | map(select(.done | not))"},
    "pending_of": {"params": ["kind"], "expr": "pending | map(select(.kind == $kind))"}
  },
  "compiled": [ /* compiled views (below) */ ],
  "loop": { /* the loop contract (below) */ },
  "nodes": [                                // node presets shipped with the module, bound at mount with module-relative fills
    {"preset": "alpha-record", "subject_expr": ".subject",
     "fills": [{"node_id": "record", "path": ["entries"], "op": "set_by_key", "key_field": "id", "expr": ".result"}]}
  ]
}
```

Validation is loud, at save and at upload: every view compiles inside the emitted
prelude against the served schema; an optional [`loop`](#the-loop-contract) names
existing views with the right arities; an optional [`compiled`](#compiled-views) view
names a declarations item array and its `key`/`expr` properties; and every node fill is a
valid fill whose path lies inside the served fragment and obeys the regimes. The first
violation raises with the offending rule and path named — never a silent accept.

### Views and the mount envelope

A module's `views` are a jq library shared by every node and prompt input on a state that
mounts it. Each view compiles into a `def <module>_<view>(…)` in a prelude prepended at
the one jq compile seam, so a node expression calls it by that name — the identifier form
maps `-` to `_`:

```
mount("s"; "alpha") | alpha_pending_of("status")
```

Every view takes the mount **envelope** as its input. The generic locator
`mount($state; $module)` in the prelude returns:

```json
{"state": "…", "module": "…", "path": ["…"], "parameters": {"…": "…"}, "declarations": {"…": "…"}, "data": "…"}
```

`.data` is the mounted subtree (a `getpath` over an unseeded state answers `null`, never
raises), `.declarations` are the values the mount stored, and `.parameters` are the
resolved parameter values — so a view reads a client's declarations by name with no
second seam. **Sibling views are called by relative name** — `pending_of` above calls
`pending` — because each `<module>_<view>` def nests every sibling def (dependency-first,
unprefixed) around its own body. Emission is deterministic (modules and views in a fixed
order) so the compile cache hits, and a module mounted twice emits its defs once.

Every jq input also carries **`.mounts`** = `{<state>: {<module>: {path, parameters,
declarations}}}` — the data the locator reads — resolved from the run scope like `.run`.
Outside a run (a validation-time compile) `.mounts` is `null` and the validation doors
pass the prelude explicitly. Views and `.mounts` are **read-only**; nothing derived is
ever stored.

### Compiled views

A `compiled` entry turns a jq string a client writes **in a mount's declarations** into a
generated view, compiled once at mount time rather than evaluated from data at run time. Each
entry is `{view, path, key?, expr?, params?, result?}`. Every body's INPUT is the flow
**root** and the mount envelope is bound as `$mount`, so a body reads its own subtree as
`$mount.data` and a sibling state member as `.states[$s]…`; a bare `.data` read is refused (its
input is the root, so `.data` would silently answer `null`).

Two forms. The **dispatch** form (`key` set): `path` reaches an item array in the declarations
schema, each item's `key` property heads a branch, and the branch body is the jq at the item's
`expr` **DOTTED** property path (e.g. `expected_input.via`; a null or absent value contributes
no branch). `key` is a single item property OR a **LIST** of properties — a list matches the
joined `"<v1>.<v2>…"` and the caller passes the same join, so a phase key unique only per
`(kind, key)` dispatches on the composite `["kind", "key"]` (`"<kind>.<key>"`) without two
kinds sharing one branch. Mounting emits `def <module>_<view>($k; $mount[; <params>]): if $k
== "<key1>" then (<expr1>) elif … else null end;`, so a node calls it as `mount("s"; "alpha") |
alpha_<view>("<k>"; .)` — `.`, the flow root, passed as `$mount`. An unknown key answers
`null`.

The **scalar** form (`key` absent): `path` reaches a single jq string property whose value IS
the body, emitting `def <module>_<view>($mount): (<expr>);` (`null` when the string is absent),
called as `mount("s"; "alpha") | alpha_<view>(.)`. `params` are extra positional parameters
emitted after `$k`/`$mount` and bound by the caller.

A body may call the module's other views and `mount(…)`. `result` declares the value shape the
body must yield — `"boolean"` (a predicate) or `"string"`. Each body is compiled at mount, on a
declarations `PATCH`, and on a module replace; a non-compiling one refuses the mount, naming
`<path>[<key>=<k>].<expr>` (dispatch) or `<path>` (scalar). When `result` is declared the mount
also EVALUATES each body over a sample flow root whose mounted `.data` is an instance
synthesized from the module's schema (an object becomes its properties, an array `[]`, a string
`""`, a number `0`, a boolean `false`, a nullable slot `null`); a value whose type contradicts
the declared `result` refuses the mount, naming the item and the value it produced, and a body
that raises over the sample root refuses likewise.

### Trace, declarations, and the effective schema

Three parts of a module are platform-owned and documented with the
[platform state store](/concepts/states#modules-and-mounts): under a **traced** mount
the platform stamps a `_trace` object (`meta`, `run`, `turn`, `inbound`, `at`) on every
object a fill writes — the engine supplies `meta: {node: <node id>}`; a module's
**declarations** carry static values a view reads as
`.declarations`, validated by their own schema and an optional `check` predicate; and the
platform composes each mount's fragment into the state's **effective schema**, which
every write validates against.

### Mounting node presets

Mounting a module is a platform operation (see
[modules and mounts](/concepts/states#modules-and-mounts)). When the module's `flow-views`
document ships **node presets**, the mount also materializes one flow binding per
`nodes[]` entry — its fills translated to absolute paths (the mount path plus the
module-relative one) and tagged with the mount for display, scoped with a generic
`scope_expr` of `.state == "<state>"`. Unmounting removes the materialized bindings. A
materialized binding is derived, not editable directly: attempting to bind a shipped
module node by hand is refused — *"flow 'f' is a shipped node of a module mounted on
state 's' — its binding is derived from the module's views; edit the mount on the States
page instead"*.

**Binding scope.** `scope_expr` is a generic jq predicate over the run's raw kwargs,
evaluated **first** in the per-binding loop at mint — before the subject is resolved. A
`false` result skips the whole binding (its fills and its refresh) and records a
`binding_skipped` state-change event; a non-boolean raises; unset means always engaged.
This is how one shipped module preset, bound by mounts on several states, writes only the
state its caller names.

### The loop contract

A module may declare an optional `loop` block — the contract the Router card's loop mode
consumes:

```jsonc
"loop": {
  "seed": "alpha-seed", "record": "alpha-record", "outcome": "alpha-outcome", "mint": "alpha-mint",
  "talk": "alpha-talk",                                         // optional composed-talk preset
  "views": {"anything_due": "anything_due", "due": "due", "due_set": "due_set", "expectations": "expectations"},
  "manifest": {"intents": ["intents"], "phases": ["phases"], "talk_slot": ["talk_slot"]},   // paths INTO the declarations schema
  "max_iterations": 20
}
```

`seed`/`record`/`outcome` (and optional `mint` and `talk`) are preset names; `views` names
existing views by their required loop arity (`anything_due(run)`, `due(kind; phase; run)`,
`due_set(run)`, `expectations(run)`); `manifest.intents`/`.phases` are paths into the
declarations schema whose array items declare the required fields (`kind`, `description` /
`key`, `kind`, `handler`), so the Studio reads them without jq. An optional
`manifest.talk_slot` is a path to an **object** property (carrying a `prompt_ref`
content-store template id and a `transcript_window_lines` bound) in the declarations schema that
turns on the module's composed-talk slot, which the optional `talk` preset speaks after the
fixed parts; a null slot means the module has no talk slot. Each
loop preset (and each phase handler) must return its value under **exactly one**
`return_result` node — the loop reads a preset output through a single envelope unwrap
(`.result | [.[]] | first`), so a preset that flags two surfaces has no single value to read. The
contract's shape and validation are defined here; the Router card's loop mode reads it to
generate the loop.

### Shipped module seeds

A module can ship as a default. On boot the seed applier reconciles the store against the
registered seeds by a content hash: it **creates** a module when absent, **upgrades** one
still equal to its shipped hash whose shipped body has drifted, **skips** an
operator-edited module (its hash no longer matches — left untouched, logged), and
**deletes** a retired name that is still unedited (an edited or still-mounted one is kept
and logged). An operator upload clears the shipped hash, so a later upgrade never clobbers
a hand edit.

## Upload — one door, two kinds

`POST /api/babelfish/upload` is one door for the flow engine's two self-describing
document kinds — the JSON's `kind` routes it. State and state-module documents are
uploaded from the platform [States screen](/studio/screens#states) instead, through the
platform's own [`/api/states`](/concepts/states#the-http-surface) doors:

- **`flow`** / **`node`** → a preset over the `flow` base tool, through the same
  in-process authoring path the preset HTTP doors use (create for a new name, a new active
  version for an existing one — earlier versions kept). A **`node`** additionally writes
  its palette tool-meta overlay: the `palette-node` tag lists it in the custom-node
  palette, an optional `folder` places its card, and a `module: <name>` field writes the
  `module:<name>` grouping tag so the palette and the module's page group it under the
  module. The overlay is merged, never replaced, so an operator-added tag survives a
  re-upload.
An unknown or missing `kind` is `422`; the response is `{kind, name}` (plus `version` for
a preset). The flow-side binding and `flow-views` documents have direct routes too:
`GET /api/babelfish/bindings` and `PUT/DELETE /api/babelfish/bindings/{state}/{flow_name}`
(plus `POST /api/babelfish/bindings/move`), and
`GET /api/babelfish/views`, `GET/PUT/DELETE /api/babelfish/views/{module}` (PUT honors
`?replace=`). Every one answers the same gated refusal (`503`, `reason:
states_unavailable`) when the flow states feature is off.

## Shipped defaults are files

The shipped defaults live as files beside the code: one JSON document per default (each
with its `kind`), a `retired.json` withdrawal manifest (`{presets, modules}`), and a `<name>.md` prose note beside each
document. A loader reads the folder at import and turns `node`/`flow` files into preset
seeds and `flow-views` files into flow-views seeds; both are applied **in-process** through
the same seed appliers the upload door's writes reach — never by the server calling its
own HTTP. The document is the source of truth, and a default is told from an operator edit
by a content hash. The platform module documents a state module pairs with ship as
platform state-module seeds on the [state store](/concepts/states#modules-and-mounts).

## Checkpoint retention

A run's pause/resume memory lives in its durable checkpointer, and on the
`postgres` provider that history is kept until a thread is explicitly deleted —
so completed and abandoned runs accumulate. An opt-in retention window bounds
them, mirroring the states record-retention idiom: configure the window, then
drive an explicit prune on a cadence (a schedule or your own cron) — never a
silent background loop.

```bash
FLOW_CHECKPOINT_RETENTION_DAYS=90
```

`POST /api/babelfish/checkpoints/prune` reaps every thread whose newest
checkpoint is older than the window and answers `{pruned, provider}` — plus a
`reason` whenever it did nothing. A **live async park is always spared**, whatever
its age; on this provider the window also doubles as the park-admission horizon, so
an async ask whose deadline lies beyond it is refused loudly at suspend rather than
parking a run whose checkpoints could be reaped before the answer arrives. Under a
bounded window an ask carrying **no** deadline is refused too — a park that cannot
be proven durable is never admitted.

| Variable | Default | Effect |
| --- | --- | --- |
| `FLOW_CHECKPOINT_RETENTION_DAYS` | unset | Day window the checkpoint prune reaps past, and the park-admission horizon on `postgres`; unset = keep forever, prune is a no-op. |

A non-positive value, or one past the integer ceiling, is a loud configuration
error rather than a silently ignored setting.

<Note>
The sweep covers the `postgres` checkpoint provider only. On **any** other provider
it reports a benign no-op naming that reason — `redis` bounds itself with its native
idle TTL (`LLM_PROVIDER_CHECKPOINT_TTL_MINUTES`), and `memory`/`sqlite` are dev-only
and never durable enough to park on at all.
</Note>

<Warning>
The prune sweeps the checkpoint tables, which the `postgres` provider shares with
every other graph pointed at the same connection — conversation and agent threads
included. It reaps any aged, unparked thread it finds there, not only a flow's. Point
the flow checkpointer at its own database if that blast radius is not what you want.
</Warning>

## Agent session continuity

By default every agent a runnable invokes gets a fresh agent thread per call. A
runnable may instead opt into **per-node session continuity**, keying that node's
agent runs to one retained session so memory carries across successive runs of the
node. The key is a plain-string template — placeholders for the flow-run id and the
node's raw id are substituted at run time, and the engine always forces the
reserved `flow:` prefix. Because the key is keyed on the raw node id it is stable
across iterations, so inside a sequential loop each iteration resumes the previous
iteration's agent thread; a parallel loop, which would drive the same key
concurrently, is rejected at build time. Real carry-over needs a
checkpointer-backed agent — a memoryless agent still runs but remembers nothing.

## How it plugs in

It installs like any other plugin: it registers its **Flows** page and the API
behind it under its own route mount, and integrates with the Studio the same way
every plugin does.

The bundle is committed inside the distribution, so installing it needs no
JavaScript toolchain on the server. The plugin ships its own HTTP API under its own
route mount and claims no backend — see [Studio plugins](/studio/plugins) for how the
Studio loads a plugin bundle and pins it.

## Organizing flows

Because a flow is an ordinary tool, it organizes through the platform's
[tool-organization overlay](/concepts/tool-organization) — the same folders,
display names, tags, and visibility that apply to any tool. The Flows page renders
that overlay directly:

- **Folders and breadcrumbs.** The page is a current-directory explorer: a
  breadcrumb, the folder's subfolders, then the flows filed there, with unfiled
  flows at the root.
- **Display names and tags.** Each flow shows its display name (its real tool name
  stays visible) and is filtered by its merged tags — a flow's plugin-native
  `babelfish` tag unioned with your editable user tags. A tag filter and a search
  box narrow the list. A tool's display name from that same overlay also surfaces
  inside the flow editor: a tool node's canvas label shows it, the node-editing
  tool pickers show it with the raw name kept visible, and the run popup and
  history inspector show it with the raw name in parentheses.
- **List or card view.** A toggle switches between a compact list and a card grid;
  the choice persists per browser.
- **Per-flow editing.** A flow row edits its display name, tags, and folder in
  place. Hiding a tool is centralized on the [Studio Tools
  screen](/studio/screens), not here — the Flows page manages everything except
  visibility.

The Flows page derives its entire view state — the open flow, the current folder,
open dialogs, and the active filters — from the URL, so a flow is bookmarkable and
shareable and the browser's back button works. A link to a flow that no longer
exists renders a loud not-found card rather than a blank editor.
