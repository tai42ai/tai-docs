The HTTP API is the operator surface of a running server. Every route lives
under `/api/*`, takes and returns JSON, and authenticates with an API key. The
per-endpoint pages in this section render directly from the server's OpenAPI 3.1
specification, so they never drift from the code.

## Base URL

The API is served by the running server, alongside the MCP endpoint and the
Studio. Prefix every path with the server's address:

```
https://<your-server>/api
```

A local server started with `tai serve` answers at `http://127.0.0.1:8000/api`.

## Authentication

Every request carries an API key in the `x-api-key` header. Mint and manage keys
with `tai keys` or the `/api/auth/api-keys` routes.

```bash
curl https://<your-server>/api/tools \
  -H "x-api-key: $TAI_API_KEY"
```

A missing or invalid key returns `401` with the error envelope below.

<Note>
  A key's access-control condition scopes what it may call. See
  [access control](/concepts/access-control) for the policy model.
</Note>

## Response envelope

Successful responses wrap their payload in a `data` field:

```json
{
  "data": { "...": "the endpoint's result" }
}
```

Errors return an `error` field carrying a human-readable message:

```json
{
  "error": "missing or invalid api key"
}
```

The two envelopes never mix — a response carries `data` or `error`, never both.

## Expression fields

Some string properties in the schema hold a **jq expression** rather than an
ordinary value. Those properties declare themselves: each carries an
`x-tai42-expression` vendor annotation, so a client recognizes the field as an
expression and learns its input and output without guessing from the field name.

```json
"condition": {
  "type": "string",
  "x-tai42-expression": {
    "language": "jq",
    "label": "condition",
    "blurb": "the declaring surface's input document",
    "returns": "truthy to proceed; a falsy result gates the surface's action off"
  }
}
```

`language` is always present and is `jq`. The rest describe the expression's
context and are emitted only when the declaring surface supplies them: `label` is a
short name for what `.` is, `blurb` says what the input document is, `keys` glosses
the input's known top-level keys as `name`/`gloss` pairs, `returns` says what the
result is consumed as, `caveats` lists evaluation edge cases, and `sample` carries a
representative input document.

The annotation is metadata only. An `x-`-prefixed keyword is ignored by JSON Schema
validation, so it can never change which values a schema accepts, and a field
without one generates a byte-identical schema to a plain string declaration. A
client that does not recognize the annotation, or the `language` it declares,
renders the field as a plain string input.

<Note>
The [Studio SDK's](/reference/studio-sdk/schema-forms) `SchemaForm` acts on this
annotation directly: an annotated field renders the
[visual jq editor](/studio/jq-editor) instead of a text box, with no per-field code.
</Note>

## Error model

| Status | Meaning |
| --- | --- |
| `400` | The request body or parameters failed validation. |
| `401` | The `x-api-key` header is missing or invalid. |
| `404` | The addressed resource does not exist. |
| `500` | An unexpected server error — the body carries a correlation `error_id`. |
| `503` | The server is applying a config reload — retry shortly. |

## The reload-gated 503

When the server applies a configuration reload, routes that mutate state — and every
door that would start a conversation turn, a channel's inbound webhook included — return
`503` until the reload completes. The body sets `reloading` to `true` and the
response carries a `Retry-After` header with the seconds to wait:

```json
{
  "error": "reloading — the server is applying a config reload; retry shortly",
  "reloading": true
}
```

Retry the request after the `Retry-After` interval. Read-only routes stay
available throughout a reload.

## Unexpected errors and validation

Every error is JSON with an `error` field and nothing beyond it that could leak.
An unexpected, unhandled server error answers a uniform `500` on every serving
path — the body is a fixed envelope carrying a correlation id and no internal
detail:

```json
{
  "error": "Internal Server Error",
  "error_id": "3f9c2a1e8b7d4f60a1c2e3d4f5a6b7c8"
}
```

The `error_id` correlates the response to the server-log line that records the
full traceback under the same id; the internal exception text — hosts, file paths,
stack frames — never reaches the client. Quote the `error_id` when reporting a
fault.

On the generic operation body-validation path (the adapter's `422`) and the
connectors mutation doors, a validation failure names **which** fields failed and
**how**, never **what** you sent: the body lists each offending field's path and
its error type only, with the rejected input values stripped, so a secret
submitted in a rejected field there does not ride back out.

A door whose body is its operation's plain request model is parsed by the shared operation
adapter: a body that does not parse answers `400 malformed request body`, and a non-object body or
a model break answers `422` with the field list above (for example `POST /api/auth/principals`,
`POST /api/marketplace/install`). Every other door reads its own JSON body — the doors whose body
carries more than the model checks (for example conversation routes, messages and events, hooks,
schedules, manifest, config, presets, templates, states, tool metadata, keys, connectors, storage,
backup, setup, sub-MCP, and the agent and tool runs) and the interaction answer, reaction and callback doors — and answers one set of `400` texts:
`invalid JSON body` for a body that does not parse (a deeply nested one included), `body must be a
JSON object` for one that is not an object, and `invalid <what>: <rule>; <rule>` for a body that
breaks its model, each rule the message pydantic gives for the bound it violates. A door then names
a missing required field in its own words (`body must contain 'answer'`). Four of them answer a
model break with a fixed text instead: the three connector mutation doors (connect, reconnect,
sub-services) answer `400 invalid request body` with the failing fields' paths and types under
`fields`, and the setup door answers `422 invalid request body`. The public webhook ingress
doors (`/universal_webhook/{topic}`, `/trigger/{token}`) are not among them: they accept any JSON value and refuse a malformed one in
their own ingest envelope, `{"status": "rejected", "error": "malformed JSON body: …"}` (the
topic door's envelope also carries its `topic`).
A model's own named rule (a hook topic or a sub-MCP slug that is not one lowercase path
segment) quotes the value it refuses, so do not rely on every error response to withhold
rejected input.
