Execution-backend contract.

Exposes the ``Backend`` ABC, the ``BackendRuntime`` ABC one launch subcommand implements with
its liveness declarations, the ``CallbackSchema``, the scheduling protocol's names and models, and
the three seams a backend plugs its engine into: the ``TaskDoor`` (its queue), the ``ScheduleStore``
(its schedule storage, read back as ``StoredSchedule``; its ``ScheduleWriter`` part is the one
schedule writer) and the ``WorkerInspection`` (its worker views).

## Backend

`tai42_contract.backend.base.Backend`

```python
class Backend(ABC)
```

Abstract execution backend for a Tai app.

A backend runs the task runtime (``launch``) and executes the work its
workers pull from the broker. The app core depends only on this interface
and stays backend-agnostic; concrete backends (celery/rq/arq) implement it
and register via ``@tai42_app.backends.register_backend``.

Fleet propagation of config changes is not a backend concern: it is the
app's own worker bus, internal to the app. A backend-runtime process
receives fleet ops through the app's bus subscription exactly like a serving
HTTP worker — the backend carries no control-plane surface of its own.

Each backend declares its own drain bound (`drain_timeout`); the app
announces it, together with its own shutdown bounds, when the process leaves,
so a fleet restart waits for the worker to finish its in-flight work rather
than reporting it timed out.

### Members

#### drain_timeout

`tai42_contract.backend.base.Backend.drain_timeout`

```python
drain_timeout: float
```

How long, in seconds, this backend's worker may take to finish its in-flight work and exit when stopped.

Read at call time, so a settings change applies to the next stop.

## BackendRuntime

`tai42_contract.backend.runtime.BackendRuntime`

```python
class BackendRuntime(ABC)
```

ONE launchable runtime of an execution backend, named by its launch subcommand.

The vendor binding answers only "how MY engine starts, drains, and
recycles"; readiness gating, signal wiring, drain-on-cancellation and pool
turnover belong to the host base that drives this object. The liveness
signal is the host's too: the runtime declares which kind it has
(`liveness`), and a progress runtime reports from its own loop.

A runtime runs only on the objects its `build` produced. The host re-imports the
package a runtime comes from on every config reload, so that the package's registrations
re-fire into the new configuration, and a reload can land between `build` and the run
body as well as during it. The runtime is a process-lifetime object and stays whole across
those re-imports: it holds what it built and never resolves its own objects again through
the import system. It hands its engine the objects themselves wherever the engine's interface
takes an object; it imports nothing of its own package after `build`; the state its
engine reads lives on the objects it built, never in its package's module globals; and it
connects receivers to an engine's process-wide signals from `build`, never at import.

Where an engine's interface takes only an import path (a setting that names a class, a stored
job that names its function), the engine resolves that name itself, possibly after a reload,
and so may reach the re-imported copy. An object handed over by name therefore keeps no state
of its own: it reads what it needs from its arguments, from the objects the build produced
that the engine passes it, or from the process environment, so the re-imported copy behaves
as the built one.

#### pool_turnover_required

`tai42_contract.backend.runtime.BackendRuntime.pool_turnover_required`

```python
pool_turnover_required: bool = False
```

True when work executes in worker processes that PERSIST ACROSS JOBS and
therefore hold a snapshot of this process's tool registry: a registry
mutation does not reach them, so the pool must be turned over. False for a
runtime that runs work in-process, and for one that spawns a fresh child per
job (the next child inherits the mutation).

Declared per class like the rest, but deliberately NOT a ``ClassVar``: a
launch option can decide whether this engine's pool persists, so an instance
may set it. The host therefore reads it off the live runtime.


#### process_prelude

`tai42_contract.backend.runtime.BackendRuntime.process_prelude`

```python
process_prelude: str | None = None
```

The ``module:callable`` the process must have run before any other import, or ``None``.

Declared by a runtime whose engine reshapes the interpreter's blocking primitives (its
threads, locks, sockets and sleeps) and so must do it before any other module has bound
them. The host's entry runs it, with no arguments, first thing in a fresh process, and the
launch refuses a runtime whose prelude this process was not started with
(`ProcessPreludeRequired`). Not a ``ClassVar``, like `pool_turnover_required`:
a launch option can decide it, so the host reads it off the live runtime.


#### liveness

`tai42_contract.backend.runtime.BackendRuntime.liveness`

```python
liveness: Liveness
```

How this process signals it is alive. REQUIRED: the host refuses a runtime without it.

A consuming runtime declares `ProgressLiveness`: what it is alive for is consuming,
and its loop is what consumes. An HTTP server declares `HttpLiveness` with the path
an orchestrator's HTTP probe requests.

#### report_progress

`tai42_contract.backend.runtime.BackendRuntime.report_progress`

```python
report_progress(self, *, next_within: float) -> None
```

Report one pass of this runtime's engine loop and promise the next one within ``next_within`` seconds.

Called from inside the loop on every pass, idle or busy, from any thread. ``next_within``
is the loop's own sleep or poll bound for the pass that follows; the probe judges this
process against it, so a loop that stops passing stops reporting and is seen as such.

binding, or one that declares `HttpLiveness`) and ``ValueError`` when
``next_within`` is not positive.

#### request_drain

`tai42_contract.backend.runtime.BackendRuntime.request_drain`

```python
request_drain(self) -> None
```

Stop accepting new work, let in-flight work finish, and make the run body RETURN once drained.

Called from the loop thread — while a ``worker_thread`` body runs on
another thread — so it MUST NOT block and MUST NOT touch
main-thread-only APIs (``signal.signal`` above all: the host owns the
process's signal disposition and a vendor rebind destroys it).

MUST BE IDEMPOTENT: the host calls it on signal AND again on the
cancellation path. Escalation belongs to `request_terminate`,
never to a second ``request_drain``.

REQUIRED iff ``consumes_work``.


#### request_terminate

`tai42_contract.backend.runtime.BackendRuntime.request_terminate`

```python
request_terminate(self) -> None
```

Cold stop: abandon in-flight work now. Called on a repeated signal.

Default: report that this runtime declares no cold stop and let the warm
drain continue — the supervisor's kill is the backstop.


#### turn_over_pool

`tai42_contract.backend.runtime.BackendRuntime.turn_over_pool`

```python
async turn_over_pool(self, *, reason: str, budget: float) -> None
```

Replace every worker that predates the mutation named by ``reason``, and CONFIRM it.

On return, no pre-mutation worker may take new work; one still finishing the
job it holds exits after it, and is not waited for. Raise loudly if it
cannot be confirmed within ``budget`` seconds — the
caller is inside a fleet-op apply, and a raise makes that op report
``failed`` rather than a false ``applied``.

Called from the fleet-op hook, which the host wires BEFORE `build`
so an op landing during a long boot is not missed. So this may run before
the engine objects exist, and it runs CONCURRENTLY with the run body once
they do. A no-op is the correct answer whenever there is no pool yet, or
the live pool turns out not to hold a snapshot: the workers that do not
exist cannot be stale, and the next ones are built after the mutation.

REQUIRED iff ``pool_turnover_required``.

**Parameters**

| Parameter | Type | Default | Description |
|---|---|---|---|
| `reason` | `str` | — | — |
| `budget` | `float` | — | — |


#### aclose

`tai42_contract.backend.runtime.BackendRuntime.aclose`

```python
async aclose(self) -> None
```

Release engine resources once the run body is done with them.

Always awaited, on every exit path. Default: nothing to release.

The run body has normally LEFT by then, but there is one exception the
binding has to survive: a blocking body cannot be cancelled, so a
cancellation that arrives while it is still on its thread abandons it
there (the host reports this) and teardown runs anyway. Release what can
be released without assuming the body let go.

Concrete rather than abstract: a runtime that owns no resource must not
be forced to declare an empty override.

## ScheduleCreate

`tai42_contract.backend.scheduling.ScheduleCreate`

```python
class ScheduleCreate(ParkableDoorMixin)
```

Create a schedule that runs ``tool_name`` on ``cadence``, or once now when no cadence is given.

``tool_kwargs`` are the arguments each fire passes to the tool, the tool's alone and forwarded
untouched — a tool whose OWN argument is named ``subject`` carries it here like any argument.
``subject`` is the OPTIONAL top-level door field naming the ``schedule``-door state context each
fire re-establishes: the create door stamps it onto the job, and the fire keys its state writes and
parks on it (it never reaches the base tool). ``state_binding`` is the OPTIONAL door-layer binding
the fire applies around the started tool alone (never the base tool's). ``schedule_name`` names a
recurring schedule; without it the door derives one from the tool, its arguments and the cadence.

A schedule is a parkable-driving door: it carries the four `ParkableDoorMixin` jqs
(``start_expr`` builds the fired tool's kwargs; ``cancel_expr`` / ``resume_expr`` act on the run's
parked interactions; ``extras_expr`` builds the started run's extras), each evaluated over the
fired tool's arguments with the run's parked interactions bound as ``$parked``. Any contract jq
needs an ``execution_key`` (the api-key ``user_id`` the recurring fire runs as, so a park it
raises can be rebound and resumed under that authority).

|---|---|
| `model_config` | — |
| `tool_name` | `str` |
| `tool_kwargs` | `dict[str, Any]` |

| `schedule_name` | `str \| None` |
| `execution_key` | `str \| None` |

#### cancel

`tai42_contract.backend.inspection.WorkerInspection.cancel`

```python
async cancel(self, task_id: str, terminate: bool) -> str
```

Cancel the task ``task_id``; return what was done.

Without ``terminate`` a task that has not started is kept from running and a running one is
left to finish; with ``terminate`` a running task is stopped as well. A backend that cannot
cancel a running task without stopping it refuses the call without ``terminate`` for a
running task rather than stopping it. The reply says what was done; when a worker answers
that it cannot stop the task it runs, the call is refused rather than leaving the task
running behind a reply that says otherwise, and a stop the workers did not confirm within
the time the backend waits for it is reported as not confirmed, with the status the task
reached.
