The Studio's left sidebar leads with the **Dashboard** row, then groups every
feature into five intent sections:

- **Capabilities** — Tools, Agents, Presets.
- **Connections** — Connectors.
- **Doors** — Conversations, Hooks, Scheduling, Served endpoints, States.
- **Activity** — Interactions, Notifications.
- **Administration** — Members, Settings, Storage, Marketplace, Manifest, System.

Each screen drives one slice of the server's `/api/*` surface, and every screen
renders its own loading, empty, and error states rather than a blank page. This
page tours the surfaces you reach most. A [Studio plugin](/studio/plugins) adds
its own links to one of these sections, or to a single shared **Plugins** section
that follows them.

## Tools

The Tools screen lists every [tool](/concepts/tools-and-extensions) the
[manifest](/concepts/manifest) loaded — your own functions, mounted MCP servers,
the standard toolbox, and any [extension](/concepts/tools-and-extensions)
variants (a `_batch` or `_chain` branch appears as its own runnable tool).
Select one to open its run panel.

  <img className="block dark:hidden" src="/images/studio/tools-light.png" alt="The Tools screen with a list of loaded tools." />
  <img className="hidden dark:block" src="/images/studio/tools-dark.png" alt="The Tools screen with a list of loaded tools." />
</Frame>

Running a tool has two modes — a synchronous run and a detached background run.
[Running tools](/studio/running-tools) covers the trade-off in full.

The Tools screen is also where you organize the namespace through the
[tool-organization overlay](/concepts/tool-organization). The list is a
current-directory explorer: a breadcrumb, the current folder's subfolders, then
the tools filed there, with unfiled tools at the root. Each tool renders its
display name (its real name stays visible beside it) and groups by its **merged
tags** — the tool's read-only plugin-native tags unioned with your editable user
tags. A tool whose effective visibility is hidden is excluded from this list
outright — there is no toggle to reveal it; hiding is a display convenience, never
a security boundary — a hidden tool stays callable. To bring one back, set its
visibility to **Shown** from the CLI or API (`tai tool-meta set <tool> --visibility
shown`); once shown it appears here again. The per-tool **edit dialog** is the one
surface that edits all four overlay fields: display name, user tags, folder, and a
three-way visibility control (**Default** defers to the plugin's declaration,
**Shown** forces it visible, **Hidden** forces it out of the lists).

Each folder row carries **Rename** and **Move** actions; Move offers the folder
tree as a parent picker (with inline create) and excludes the folder and its own
descendants, so a folder can never become its own ancestor. Both appear only for a
session that can write the overlay.

The screen also carries the app-tool live-registry admin card — **Reload** re-registers
one app tool and **Remove** detaches it from the running registry, each named by its
reloader `kind` and `name` and applied across the fleet. Reload is non-destructive;
Remove asks the house confirm first. The card renders only for a session whose
projection reaches those fenced doors.

## Agents

The Agents screen lists the [agents](/concepts/agents) the manifest registered,
each with a **Run** entry that opens its run panel. **Compose agent** authors a
new agent as a saved spec — a prompt, a tool selection, and presets baked over a
base agent — that versions and rolls back like a [preset](/concepts/presets); the
authored-agents panel is empty until you compose one.

## States

The States screen drives the platform [state store](/concepts/states) — the
declared documents every door reads and writes per subject. It lists each declared
state with its subject kinds, record and consumer counts, and last update, above a
**Declare state** action and an **Upload** action that routes a `.json` file to the
state or state-template upload door by its `kind`.

<Frame caption="The States screen: declared states with their subject kinds, record and consumer counts.">
  <img className="block dark:hidden" src="/images/studio/states-list-light.png" alt="The States screen listing declared states with subject-kind badges and record and consumer counts." />

A **Pending saves** card sits above the list whenever the store is on: the
[pending saves](/concepts/states#pending-saves) not yet applied, refreshed every ten seconds,
with a summary of how many are outstanding and how many failed. It opens on the **Failed** tab
(or **All outstanding** when nothing has failed) and pages with **Load more**. Each row shows the
save's status badge (Pending, Calls queued, Calling, or Failed), its first subject and how many
more, the calls it runs, its run, age, attempts, and last error. A failed row offers **Retry**,
which reports whether the save applied, was queued again, or failed again, and **Discard**,
behind a confirm that warns its writes and calls will never be applied.

the base JSON Schema as a nested field tree — attached subtrees are read-only and
badged with their template — or points it at a stored template whose rendered value
is the schema, with the resolved schema shown beneath; both sit beside the subject
section (the kinds and the default kind; `person` keys are person ids from the
conversations identity store) and the retention setting. Once a state has records the editor accepts only additive
changes: removing or changing an existing field is refused.

The **Templates** tab lists the state's attachments — template, path, and the
parameter and declaration counts — with **Edit declarations** and **Detach** actions and
an **Attach template** form that renders the template's parameter and declaration schemas
as fields. Below the attachments, a **State templates** section lists the platform

## Conversations

The Conversations screen, under **Doors** in the sidebar, is the operator's window
over the [conversation bridge](/concepts/client-conversations) — every route, whichever
door it listens on, in one place. It both **manages** routes and **monitors** their
traffic, and drills down in three levels, each of them a URL you can share or bookmark:
the route picker, that route's threads, and one thread's transcript.

The landing carries three tabs — **Routes**, **Per-target configs**, and **Failed
deliveries** — so only the open one reads its door; on a no-backend deployment each
reports its own off state rather than three stacked empties.

The **Routes** tab is the route picker: it lists every route with the door it answers
(a channel's registry name, or the authed API), the identity that medium reaches you
at, and the agent or tool a turn runs. **Create route** opens an upsert dialog, and
each row edits or deletes its route. The dialog picks each name from the deployment's
own lists:

- **Target** — a **Target kind** of Agent or Tool, then an **Agent** or **Tool** picker
  over the registered agents or tools. The group's help says what a turn runs: an agent
  runs each turn as a threaded conversation; a tool is dispatched once per message, with
  no thread memory.
- **Door** — Channel or API. The help explains the choice: a channel answers on its
  own medium; the API door answers to a callback URL, or the caller polls. A channel
  door picks an installed **Channel** and takes **Our identity**, the address on that
  channel that clients message; its help is the channel's own hint for what to enter.
  An API door takes a **Callback URL**.
- **Execution key** — the api key each turn runs as. Every tool call the turn makes is
  authorized against that key's live grants, so prefer a least-privilege service key
  over a human's broad one. The picker lists the api keys you own (an admin sees every
  key) and offers an api-key session its own identity when the list does not hold it;
  an account session is told to mint a key first. A stored key outside the list is
  flagged **not a listed key**, and when it is not the session's identity the dialog
  says so before save (for a non-admin, that the server will refuse it). With access
  control off the dialog has no Execution key field, and the route runs as the gate-off
  identity.

A stored value the deployment no longer lists stays selected and is flagged — **not
registered** for an agent or tool, **not installed** for a channel — with "Pick
another, or saving is refused." When the deployment lists none, the picker says so
and links to the Agents screen or to the marketplace's plugins or channel plugins; a
picker the session may not list shows which read it needs.

The rest of the route is authored through a schema form whose rules come from the
contract's published route document: a route name of lowercase letters, digits and
hyphens, an optional absolute `https` callback URL with no user name or password (leave
it blank for a poll-only route), a `:`-free channel name, and an error reply of up to
2,000 characters. A value that breaks its rule is refused in the form with that field's
own message, before anything is sent. Either target kind carries the route's jq programs — `start_expr`,
`reply_expr`, and the door-contract `cancel_expr` / `resume_expr` / `extras_expr` —
each rendering the [visual jq editor](/studio/jq-editor) in place. An
`api`-door save that sets a `callback_url` mints a fresh `callback_secret` and **reveals
it exactly once** in the dialog under a loud caption — every such save rotates it and no
door can re-read it, so copy it then; a `channel` save and a poll-only `api` save (no
`callback_url`) carry no secret and close straight away.

The thread list also lets an operator **reset many threads at once**. Each row carries
a checkbox, and a header checkbox ticks or clears every currently loaded row (and shows
a mixed state when only some are ticked). The selection is always the rows on screen —
"select all" means the loaded page, never an unbounded server-side set. A
**Reset selected (N)** danger action, offered only to a session that may delete on the
route, forgets every ticked thread behind the house confirm, whose copy and confirm
label both name the count and state that each thread's transcript and the agent's memory
of the conversation are forgotten and that it cannot be undone. The reset fans the
same per-thread [delete door](/reference/conversation-bridge#forgetting-a-thread) out one
thread at a time — there is no "reset everything matching a filter" server action.
Results are reported **per item**: threads that reset cleanly drop from the list, while a
thread whose reset failed — for example a `409` because a turn is in flight — stays as a
failed row carrying its reason and a **Retry**, so a partial failure is visible and
recoverable thread by thread.

A transcript **live-tails**: it re-reads the newest page every few seconds, so a new
exchange lands with no interaction, and the foot of the pane says so. **Load older
messages** pages backwards through history; past a few pages of history the tail
pauses — it says it has, and **Jump to latest** puts it back on the newest page and
resumes it. The thread list refreshes on its own cadence and pauses the same way
when paged deep, with **Back to the newest** to resume.

Each exchange renders the visitor's message verbatim as plain text, the agent's
answer as markdown, and two chips: the answer's outcome and its delivery state.
When the visitor's message carried inbound attachments, they render in the visitor
bubble beside the text — an image inline, a document as a labelled download card,
and audio or video in a native player — each loaded from the platform's own
served-media reference. A `failed` delivery takes the danger tint plus a rule down
the exchange, so a failure never reads as an ordinary row. An admin also gets a **Delivery detail** disclosure
carrying the attempt count, each part sent with its length and provider message ids, and
the retained error.
A message an operator sent [by
hand](/reference/conversation-bridge#operator-messages-and-control-mode) (its record's
`origin` is `operator`) has no visitor side: it shows as one bubble on the agent's
side, labelled **Operator** and set apart by an accent border, so a human's reply reads
as distinct from the flow's.

A message the platform sent on its own (a [send
record](/reference/conversation-bridge#send-records)) is a bubble on the agent's side,
labelled by what the record proves. A send made inside a turn to its participant is drawn
inside that turn's exchange, labelled **Agent**, or **Agent · question** for a question.
Any other send is its own exchange, in neutral colours with a dashed border, labelled
**Sent message**, **Question**, **Platform notice** or **Channel notice**. A question's reply
over the channel shows under it as **Visitor · reply**; for a question asked as sensitive it
reads "Reply received · not stored (sensitive)". A send whose outcome is unknown takes the
danger tint and the rule down the exchange, like a failed one, with the chip **Sent, outcome
unknown**.

A message that replied to an earlier one shows a quote block above it, a muted
inset with a leading rule: **Replying to** and the quoted text in full. When the thread's
record does not hold the quoted message it reads "Replying to a message this thread's record
does not hold. It may be in an earlier thread of this conversation, whose text is not shown
here, or it expired, was forgotten or was never recorded." with the message id; a quote of
an answer to a sensitive question reads "Replying to an answer to a sensitive question. Its
text is not kept."; a quoted message with no text reads "Replying to a message with no
text." A reply to a question shows the same block on its **Visitor · reply** bubble.

Beside the transcript, an open thread carries two operator actions over the otherwise
read-only monitor:

- A **control-mode** toggle — *Agent replies automatically* — reads the thread's
  [mode](/reference/conversation-bridge#control-mode) and flips it between `agent` (the
  flow answers new messages) and `manual` (new messages wait for a human).
- A **compose box** at the foot sends a reply into the thread by hand, delivered from
  the route identity; on success the tail shows it at once.

Both are the door's **write** action. A capability-scoped or read-only session may set
neither: the refusal is shown inline, never swallowed.

An open thread also carries two destructive actions, each behind the house confirm:

- **Delete thread** forgets this one thread — its transcript records and the agent's
  checkpoint memory of it — so a later message on the same address starts fresh.
- **Erase person** is the GDPR right-to-erasure action, offered only when the thread's
  transcript names a linked person. It erases the person entirely — their aggregated
  thread and checkpoint, their person row, and every address-to-person link — across
  every route they ever wrote under. The confirm states that blast radius plainly. A
  thread whose transcript reads as not found (every record pruned) names no person, so
  the action is not offered there; erasure stays reachable through
  `DELETE /api/conversations/persons/{person_id}` and the CLI.

## Marketplace

The Marketplace screen browses the [marketplace](/marketplace/index) plugin
index through the server. A Browse tab runs an item-level search with facet
chips for kind, category, and tags and a sort control; an Installed tab lists
the plugins this server has installed and their update availability.

Selecting a listing opens its detail — the items it carries, its version
history, its description, and homepage and repository links; when the plugin is
installed, any security advisories affecting the installed version show there
too. The detail drives [install, update, and
uninstall](/marketplace/install) against the server's `/api/marketplace/*`
routes, with progress surfaced in place. The install, update and uninstall result
shows the fleet report and the worker recycle report. A session that is not an
administrator sees, in place of Install, Update or Uninstall on a plugin's page and of
**Upgrade all** on the Installed tab, a line naming the route it lacks.

## Connectors

The Connectors screen, under **Connections**, is the directory of outside apps and
MCP servers. A search box and filter chips narrow it; each card is marked
**Installed** or **In marketplace**, and the marketplace listings load page by page
with **Load more**. A provider card lists each of its [connections](/concepts/connectors)
with its tools, a **Pick tools** action and a **Fix** action for a connection that
needs it, and **Add another account** for a second account. Connecting runs three
steps: connect, sign in, pick tools; a sign-in that redirected the whole tab resumes the
flow back here. Installing a marketplace listing happens inside its Connect step and
needs an administrator; any other session sees a line naming the install route in
place of the listing's Connect. Below the directory sit the connections list and
**Add a custom server**.

The picks are the MCP entry's `include` / `exclude`:

- A server in exclude mode stays in exclude mode when its picks are saved. In exclude
  mode a Save with nothing ticked is allowed (every tool the server lists now is
  unmounted; tools it adds later mount); in include mode at least one tick, or
  **mount every tool**, is needed.
- A name the server no longer advertises shows **Not advertised** and stays picked
  until unticked.
- A picked tool that is not mounted says why: the server failed, a preset owns the
  name, its input schema cannot be used, or the server did not list it at the last
  load.
- Unticking a tool a preset or another reference uses is refused (see [Unpicking a
  used tool](/concepts/manifest#unpicking-a-used-tool)), and the section lists those
  holders as links.
- With several sub-services, one Save writes them one after another, and **Save
  remaining** retries the rest after a failure.

A session missing a read sees the directory draw what it can read, with a line naming
each missing route.

## Manifest

The Manifest screen, under **Administration**, is the config-artifact inspector. It
holds:

- **The manifest** — the preserved [manifest](/concepts/manifest) document the server
  loaded, `!ENV` markers intact, as an expandable tree.
- **MCP servers** — every mounted MCP server, healthy or failed, each with a
  **Reload** control (a failed server can be reloaded, or deregistered, in place), and
  the configuration editor that writes the manifest's `mcp` array: a form view (one
  editor per entry: a schema-driven transport form plus a tool composer for the
  `include` / `exclude` lists) and a raw-JSON escape hatch over the same working list.
  A connector-owned entry renders read-only — it is kept in sync by its connection, so
  you remove it by disconnecting. A malformed edit is a loud inline error and no
  request is sent.
- **Extensions** — the extensions the server loaded, grouped by kind, and the
  manifest's extension settings: `extensions_modules`, `backend_module` and the
  per-tool extension maps of `tools`, `mcp` and `api_tools`. Extensions are attached to
  a tool on its Tools page or in a preset; see [Tools and
  extensions](/concepts/tools-and-extensions).
- **Section doors** — the `tools` and `agents` per-entry add and remove controls (an
  entry is added by pasting its JSON with its title validated, removed by naming its
  title), and the `api_tools` include/exclude curation (a name is added to or removed
  from a list).

Every write crosses the config pipeline and reloads the fleet, so a save re-reads the
artifact and reports any failed propagation; removes ask the house confirm. Each door
renders only for a session whose projection can reach it. (The derived sub-MCP servers
live on [Served endpoints](#served-endpoints).)

## The scoped Studio

There is one Studio, not a separate portal per role. When you sign in with an
[owned key](/concepts/owned-keys) — a capability-scoped credential rather than a
full-privilege one — the shell renders from that key's **capability projection**
(`GET /api/auth/me`): the sidebar trims to the features the key can reach, each
list slices to what its scopes cover, and the data-bearing inboxes filter to the
key's own identity. Nothing is hidden by the client; the projection is the same
derived, jq-exact view the request gate enforces, so the UI never shows a door
the server would then deny.

The screen below is the same Tools screen as above, but signed in as an owned key:
the sidebar carries only Tools, Interactions, Notifications, and Settings — the
operator surfaces (Dashboard, System, Marketplace, and the rest) are gone. This
key's projection reaches the tool surface, so its catalog is the full list; the
scoping visible here is the **trimmed navigation**, and the genuinely sliced views
are the identity-filtered inboxes below. A key whose scopes did not reach the tool
surface would list fewer tools — or carry no Tools link at all.

## The rest of the sidebar

Every screen follows one of a few layouts; a screen with tabs under its header
(Settings, Dashboard, Marketplace, the Conversations landing) has one per tab:

- **Browse and inspect** — a list beside the open item's detail, the selection kept in
  the URL: Tools, Presets, States, Storage, and a Conversations route with its threads
  beside the open transcript.
- **Catalog** — a directory of cards with search and filters: Connectors, the Tools card
  view, and the Marketplace Browse tab.
- **Registry** — records in tables or lists, with create and row actions in dialogs
  and a destructive action confirmed before it runs: Scheduling, Members, the
  Conversations Routes and Per-target configs tabs, the Marketplace Installed tab, and
  the Profiles, API keys and Roles tabs of Settings.
- **Registry with inline create** — the records first, then the create forms on the
  page below them: Hooks and Served endpoints.
- **Replaced detail** — one item takes over the page or the tab: a Marketplace plugin's
  page, a trace on the Dashboard's Tracing tab, a state template or a state's records.
- **Run surface** — a list, then the run view in its place: Agents.
- **Inbox** — newest first, with a button at the foot for the rest: **Load more** on
  Interactions, where the server pages, and **Show more** on Notifications, where the
  whole feed is already loaded.
- **Status and configuration** — stacked cards of read-only views and in-place editors:
  Manifest, System, the Dashboard tab, the Settings, Environment and Backup tabs of
  Settings, and the Conversations Failed deliveries tab.

The screens not toured above:

- **Presets** *(Capabilities)* — [versioned tool-wraps](/concepts/presets) and their
  version history; each preset also renders and edits its
  [tool-organization](/concepts/tool-organization) display name and tags (folder
  navigation and hide controls stay on the Tools screen). See
  [Presets](/studio/presets) for the create dialog and the fixed-kwargs editor.
- **Scheduling** *(Doors)* — [scheduled tool runs](/concepts/triggers-and-webhooks).
- **Members** *(Administration)* — the people and pending invitations of the accounts
  providers, with the actions they declare; see
  [Members](/studio/admin-console#members).
- **Settings** *(Administration)* — server configuration, environment values, and API
  keys (see [Admin console](/studio/admin-console) and [API keys](/studio/api-keys)).
  An environment save of a recycle-class setting shows the worker recycle it rolled.
  A **Reload config** control re-reads env and re-initializes the deployment from its
  manifest in place, applied on the serving worker and broadcast to the fleet; a worker
  whose reload left a recycle-class setting waiting for a restart is listed with it.

### Storage

**Storage** *(Administration)* — one screen over the
[stored resources](/concepts/storage-and-resources). The storage list or the templates
list opens it, whichever your access reaches, and each action shows only where your
access and the doors the deployment mounts reach it: the storage doors serve a caller
with the storage grant, and the templates doors serve a caller holding only the
templates grant. A deployment that mounts neither, or a caller who reaches neither
list, reads "Storage is not served here".

Opening an object shows it by kind:

- **Text** — its content, with a **Render preview** where your access reaches the
  template render.
- **Document** — the extracted text, marked "Extracted text; this object is not a
  template.", with no template action.
- **Binary** — "Binary object: no text preview."

An object the server cannot show — over the size cap, text that is not UTF-8, or a
file its extractor cannot read, such as an encrypted PDF — shows the server's message
with **Download** and **Delete** still offered. **Upload** writes one text object or
a batch of files; before anything is sent it flags ids that already exist or repeat
in the batch and, for a caller who stores text only, files that are not UTF-8 text.
**Clear cache** clears the template cache and says "Template cache cleared.". Channel
media is not listed here: the server leaves it out of both lists.

A **Delete** that the server refuses because something still names the object keeps
the dialog open and lists each holder, as a link, under "Still used by — remove these
first:".
