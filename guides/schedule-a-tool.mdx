Run a tool on a schedule through the backend.

The runtime runs a registered tool periodically. A schedule names the tool, its arguments, and a cadence; a worker backend fires it on time. Scheduled runs execute on the backend, so a backend plugin must be configured for schedules to run.

## Configure a backend

A schedule runs on the worker backend, not in the request path. Register a backend plugin under `backend_module` in the manifest and start its worker runtime:

```yaml manifest.yml
backend_module: myapp.backend
```

```bash
tai backend --manifest-path manifest.yml
```

See [Backends](/concepts/backends) for where tools run.

## Attach the schedule extension

A schedule on a cadence fires the tool's `<tool>_schedule_task` vehicle — the backend's `schedule_task` [extension](/concepts/tools-and-extensions). You always name the base tool; the server resolves the vehicle. Naming the backend under `backend_module` registers that extension, but it is never attached to a tool on its own: name it in the tool's per-tool `extensions` map so the vehicle exists.

```yaml manifest.yml
backend_module: myapp.backend

tools:
  - title: my_tools
    module: myapp.tools
    include: [report]
    extensions:
      report: [schedule_task]
```

Without the extension the tool has no schedule vehicle, and `tai schedules add report --cron ...` answers a `404` — the cadence has nothing to run on. `GET /api/tools/tags` marks each tool `schedulable` when its vehicle is registered, which is how Studio's schedule dialog picks the tools it offers.

## Add a schedule

Name the base tool and its cadence. Pass tool arguments with `--tool-kw key=value` (or `--tool-kwargs` as JSON), and give the cadence with at most one of:

- **`--cron EXPR`** — a crontab expression: 5 fields (`minute hour day-of-month month day-of-week`), or 6 with a leading seconds field, which is dropped.
- **`--every SECONDS`** — an interval, in seconds (greater than 0).
- **`--cadence JSON`** — the cadence object itself (below).

```bash
tai schedules add report --cron '0 9 * * *' --schedule-name morning-report
```

With no cadence option the tool runs **once, now**. `--schedule-name` names a recurring schedule (its handle for `tai schedules delete`); it needs a cadence. Without it the server derives a name from the tool, its arguments and the cadence, so re-adding the same schedule updates it in place — pass `--schedule-name` when you want an explicit, stable handle.

### The cadence

Every door speaks one cadence shape, discriminated by `kind`:

```json
{"kind": "interval", "every": 60, "relative": false}
{"kind": "crontab", "minute": "0", "hour": "9", "day_of_month": "*", "month_of_year": "*", "day_of_week": "*"}
```

`relative` aligns an interval to its own clock. The Celery backend honours it; the arq and RQ backends cannot, and refuse a schedule with `relative: true` rather than ignoring it.

Over HTTP, `POST /api/schedules` takes the same fields:

```bash
curl -X POST .../api/schedules -H 'Content-Type: application/json' -d '{
  "tool_name": "report",
  "tool_kwargs": {"recipients": ["alice"]},
  "cadence": {"kind": "crontab", "minute": "0", "hour": "9"},
  "schedule_name": "morning-report"
}'
```

The body is closed: an unknown key is a `400`, and so is naming the `<tool>_schedule_task` vehicle as `tool_name` or giving `schedule_name` without a `cadence`.

## Driving parked interactions

A schedule can also be a **parkable-driving door**: on each fire it can cancel, resume,
take, or start runs against the [parked interactions](/concepts/asking-the-caller) on
its subject. Pass the four [door-contract](/concepts/asking-the-caller#the-door-contract)
jqs — each evaluated over the schedule's fired tool arguments with the run's parked
interactions bound as [`$parked`](/concepts/jq-variables#doors):

```bash
tai schedules add report --cron '0 9 * * *' \
  --execution-key svc \
  --start-expr '{waiting: ($parked | length)}' \
  --resume-expr '$parked[0].id'
```

- **`--start-expr`** builds the fired tool's kwargs (`null` starts nothing).
- **`--cancel-expr`** names parked interaction ids to cancel.
- **`--resume-expr`** names an ask to resume with an answer (`{id, payload}`) or a
  waiting outcome to take (a bare id).
- **`--extras-expr`** builds the `extras` mapping handed to the started target.

Any of the four requires **`--execution-key`** — the identity the fired run runs as. A
schedule fire has no receiver, so a resumed run's terminal
[waits on the subject](/concepts/asking-the-caller#waiting-outcomes) for its next owner
to take.

<Note>
A schedule created with a `state_binding` has the binding checked and its templates attached
at create, before the backend stores anything: a binding naming an undeclared state is a `404`,
an occupied attach path a `409`, and a states-store failure a `500`. See [saving a
binding](/concepts/states#saving-a-binding).
</Note>

## Inspect and remove

<Steps>
  <Step title="List schedules">
    ```bash
    tai schedules list
    ```

    Each row names the schedule, the tool it fires, its cadence, whether it is enabled, and its next run — never the stored tool arguments.
  </Step>
  <Step title="Check the server clock">
    Cron cadences resolve against the server's clock — read it to reason about when a job fires.

    ```bash
    tai schedules server-datetime
    ```
  </Step>
  <Step title="Delete a schedule">
    ```bash
    tai schedules delete report
    ```
  </Step>
</Steps>

A schedule the worker cannot recover — one that keeps failing when the watchdog tries to read or re-arm it — carries an `error` (its message and when it happened) in the listing rather than being retried silently forever, so `tai schedules list` tells you which schedule needs attention.

A scheduled run, like every dispatched job, is bounded by the backend's job budget, `<PREFIX>_TASK_TIMEOUT` (see [Backends](/concepts/backends#the-job-budget)).

<Note>
A schedule and a webhook binding are the two ways a tool fires without a client call. To fire a tool on an inbound event instead, see [Fire a tool from a webhook](/guides/fire-a-tool-from-a-webhook).
</Note>

## Manage schedules in the Studio

The Studio's **Scheduling** page lists the deployment's schedules: each row names the schedule, its cadence (`Every 3600s`, or `Cron:` and its five fields), whether it is enabled, and the tool it fires. A schedule carrying an `error` shows an **Error** badge beside its status; the badge's tooltip carries the message and when it happened. The page also shows the server clock that cron cadences resolve against.
