The **web channel** hosts a standalone chat page for anonymous visitors: it serves
the page, mints a session cookie, and bridges each message through the conversation
bridge — so a turn can answer whoever opens the page, with no vendor account and no
account for the visitor. Unlike the messaging channels it is both the chat surface
**and** the transport.

See [client conversations](/concepts/client-conversations) for the bridge model this
guide configures, and the [web channel plugin](/plugins/tai42/channel-web) for the plugin.

## Configure the channel

Load the channel module and point it at a Redis for its sessions and transcripts.
There are no vendor credentials.

```bash
CHANNEL_WEB_REDIS_URL=redis://localhost:6379/0
```

```yaml manifest.yml
channel_modules:
  - tai42_channel_web
```

## Create a route and open the page

A web route binds an **identity** — an arbitrary name you choose — to the turn that
answers it. Every route still runs its turn **as** a least-privilege `execution_key`;
mint and bind one exactly as in
[WhatsApp to an agent](/guides/whatsapp-to-agent#prerequisite-mint-and-bind-a-least-privilege-execution-key).

```bash
tai conversations create web-desk \
  --door channel --target-name support --execution-key support-bot \
  --channel web --identity desk
```

Send visitors to the chat page for that identity:

```
https://<your deployment>/api/channels/web/chat/desk
```

The page is self-contained — the plugin serves both the page and its doors — and its
full door reference lives in the plugin's own README.

## Link parameters

Query parameters on the chat page URL are **captured with the visitor's session** and
delivered to the turn. A route whose target is a **tool** receives them on its payload
under a `params` key — string values, reachable from `payload_expr` as
`.params.<name>`:

```
https://<your deployment>/api/channels/web/chat/desk?topic=support&ref=abc
```

Route to a tool and read a parameter in the payload mapping:

```bash
tai conversations create web-desk \
  --door channel --target-kind tool --target-name my_flow --execution-key svc \
  --channel web --identity desk \
  --payload-expr '{flow_graph_kwargs: {message: .message, topic: .params.topic}}' \
  --reply-expr '.result.answer // null'
```

The parameters are captured on the navigation that serves the page and ride every
later message's turn. Bounds are enforced at the door — **at most 16** parameters,
each key matching `^[A-Za-z0-9_-]{1,64}$`, each value at most **512** characters, the
whole set at most **2048** bytes — and a violation is a refused page, never a silent
trim. The names `pair` and `tai_entry` are reserved and stripped before storage. A
later navigation carrying parameters replaces the stored set; starting a new
conversation clears it. Parameter values are never logged, and the `params` key is
present on the payload **only** when the entry carried parameters.

### Parameters carry no trust

A link parameter is **transport, nothing more**. The platform carries, caps, and
never logs it, but attaches **no** trust — no signature, no expiry, no
interpretation. A parameter is text anyone can put in a URL. When a flow must *trust*
a value, it issues its **own** secret token, delivers it in the link, and checks it in
its **own** store — where expiry, single-use, and revocation live. The check is the
flow's, and jq gating in `payload_expr` runs **before** the tool does:

```bash
--payload-expr 'if .params.key then {flow_graph_kwargs: {message: .message, token: .params.key}} else error("no key") end'
```

The `error("no key")` aborts the turn when the token is absent; the tool then verifies
the token against its own store. The platform never verifies a parameter on the flow's
behalf.

## Entry gate

A web route can be **gated**: the chat page is served only to a navigation carrying a
live entry code on `?tai_entry=<code>`. An ungated route is unchanged — the gate is
opt-in per identity.

```
https://<your deployment>/api/channels/web/chat/desk?tai_entry=<code>
```

Entry codes are operator-minted, multi-use, optionally expiring, revocable, and
**hashed at rest** — only a code's hash is stored, and the raw code exists only in the
mint response and the visitor's link. A missing, unknown, expired, or revoked code —
or a client that has guessed too often — is refused with **one** page, HTTP `403`,
**one** wording: the gate is no oracle for whether a code exists. Guessing is throttled
per client.

The gate is checked only where a session is minted — opening the page or starting a
new conversation. An existing session is admitted without a code, because a session is
already a granted capability: **code expiry gates new entries only**.

<Warning>
The gate admits **whoever holds a live code** — never *who* they are. Forwarding the
link forwards entry: anyone who receives the URL enters. The gate is not identity;
identity remains the pairing's or the flow's own.
</Warning>

### Operating the gate

The gate's lifecycle is four **authed** management doors — call them with a platform
API key. Enable the gate, mint and distribute codes, then expire or revoke them.

<Steps>
  <Step title="Enable the gate">
    ```bash
    curl -sS -X PUT "$TAI_BASE_URL/api/channels/web/gates/desk" \
      -H "X-Api-Key: $ADMIN_KEY" -H 'Content-Type: application/json' \
      -d '{"enabled": true}'
    ```

    While the gate is off the route serves its page to any navigation, exactly as
    before.
  </Step>
  <Step title="Mint a code and distribute the link">
    Mint a code — optionally labelled, optionally expiring — and paste it into the
    chat URL you hand out. The raw `code` is returned **once**; only its hash
    (`code_id`) is stored.

    ```bash
    curl -sS -X POST "$TAI_BASE_URL/api/channels/web/gates/desk/codes" \
      -H "X-Api-Key: $ADMIN_KEY" -H 'Content-Type: application/json' \
      -d '{"label": "spring-cohort", "expires_at": "2026-12-31T00:00:00Z"}'
    ```

    ```json
    { "data": { "code": "shown-once-store-it-now", "code_id": "<sha256hex>", "expires_at": "2026-12-31T00:00:00Z" } }
    ```

    Distribute
    `https://<your deployment>/api/channels/web/chat/desk?tai_entry=shown-once-store-it-now`.
    A code is multi-use: everyone holding the link enters.
  </Step>
  <Step title="List codes">
    Codes are listed by hash — a raw code is never re-readable.

    ```bash
    curl -sS "$TAI_BASE_URL/api/channels/web/gates/desk" -H "X-Api-Key: $ADMIN_KEY"
    ```
  </Step>
  <Step title="Expire or revoke">
    A code lapses on its own `expires_at`, or you revoke it by its hash:

    ```bash
    curl -sS -X DELETE "$TAI_BASE_URL/api/channels/web/gates/desk/codes/<code_id>" \
      -H "X-Api-Key: $ADMIN_KEY"
    ```
  </Step>
</Steps>

<Warning>
**Revocation cuts new entries only.** Revoking or expiring a code stops it admitting
the **next** visitor — but a visitor already admitted keeps a live session until its
own TTL lapses, and activity refreshes that TTL. Revocation is **not** an eviction
tool: it does not end a session already granted. To cut off a live visitor you end
their session, not the code they entered with.
</Warning>
