Each repository in the ecosystem keeps its own `CONTRIBUTING` guide; this page points to them and states the discipline every repository shares.

The platform is a multi-repo ecosystem. The core repos define and implement the contract; the plugin repos build on it. Contributions live in the repo they touch, under that repo's `CONTRIBUTING` guide.

## The shared discipline

Every repository holds to the same rules, enforced in each repo's CI:

- **The leaf rule.** Among `tai42-*` packages, the skeleton imports `tai42-contract` and `tai42-kit` only; a plugin imports `tai42-contract` (and `tai42-kit` where it needs shared helpers) only. No plugin imports the skeleton — providers register through the `tai42_app` handle when the manifest loads them.
- **Providers stay out of the core.** Connectors, storage, config, backends, and monitoring ship as plugins that register at manifest load — never imported by the skeleton.
- **Optional drivers stay optional.** A heavy client driver reaches the engine through an extra; a module whose extra is missing fails loudly at import, never a silent skip.
- **Errors surface loudly.** A missing module, a malformed config entry, or a failed sub-step raises and propagates.
- **Typed packages.** Every package ships `py.typed` and keeps the type-checker clean.

## Develop

Every clone stands alone: a repo's dev venv installs it editable and resolves its `tai42-*` dependencies from PyPI, so no other checkout has to be present. Repos declare dev dependencies either as the `dev` extra or the `dev` dependency group — check which one the repo's own `pyproject.toml` uses.

Repos with a `dev` extra (`[project.optional-dependencies]`):

```bash
uv venv --python 3.13
uv pip install --no-sources --editable ".[dev]"
uv run --no-sync ruff check .
uv run --no-sync ruff format --check .
uv run --no-sync pyright
uv run --no-sync pytest
```

Repos with a `dev` dependency group (`[dependency-groups]`):

```bash
uv venv --python 3.13
uv pip install --no-sources --group dev --editable .
uv run --no-sync ruff check .
uv run --no-sync ruff format --check .
uv run --no-sync pyright
uv run --no-sync pytest
```

`--no-sources` ignores the `[tool.uv.sources]` overrides so the dependencies come from the index; `--no-sync` runs each gate against that environment instead of re-resolving.

See the target repository's `README` for the exact extras or dependency group it installs, and its `CONTRIBUTING` guide for the rest of its specifics — any secret scan, and its licensing statement.

## How dependencies resolve

A repo's `pyproject.toml` points its `tai42-*` siblings at `../tai-*` checkouts through `[tool.uv.sources]`, while its committed `uv.lock` pins those same siblings to released versions from the index. **The two disagree deliberately**, and that disagreement is what keeps the repos independent:

- **CI resolves the published versions.** Every CI job sets `UV_NO_SOURCES=1`, so the sources table is ignored and `uv sync --locked` asserts against the committed lock. CI clones no siblings: a repo's gate proves the repo against the artifacts a user installs.
- **Local development resolves the checkouts.** A plain `uv sync` honours the sources table and installs the siblings editable, so a cross-repo change is picked up without publishing.
- **The `uv-lock` pre-commit hook passes `--no-sources`.** A bare `uv lock` run beside sibling checkouts rewrites the committed lock to path entries and stages it, which reverts the model silently.
- **Dependabot propagates versions.** When a package publishes, Dependabot opens the bump PR — dependency range and lock together — in each dependent, and that repo's CI proves it.
- **`tai-e2e` is the exception.** It resolves siblings from their checkouts on purpose: proving the repos against each other at `main` is the suite's job, and its `fleet-e2e` status is where cross-repo drift surfaces.

A lock that records a sibling's path also records that sibling's version, so one version bump leaves every dependent's lock stale and its `main` red. Published resolution removes that coupling, and the integration suite — not each repo's own gate — is what tests the fleet together.

Testing an unreleased sibling change is therefore explicit: work locally with the sources overrides, or publish a prerelease and let Dependabot carry it.
