A backend is where a tool actually runs when it should not run inline in the
request. It is the execution engine behind background, scheduled, and distributed
tool runs — and it is swappable, so the same tool runs the same way whichever
engine you choose.

## The backend seam

The `Backend` ABC is the contract; the skeleton re-exports it as the registration
seam and ships the callback glue that chains a backend result back into the
runtime. Concrete worker backends — for example ones built on Celery, RQ, or arq —
are external [plugins](/concepts/config-and-secrets) that implement the ABC and
register through `tai42_app.backends.register_backend` when the
[manifest](/concepts/manifest) names the `backend_module`.

When a backend chains a follow-up step after a tool result, a failure in that
follow-up delivery is surfaced through the backend's own failed-job machinery —
recorded and retried under the backend's policy — rather than being discarded. A
lost follow-up is therefore visible in the backend's failed-job view, not silent.

The backend runs as its own process:

```bash
tai backend
```

A registered backend adds a separate task runtime, so the deployment is now a
fleet of more than one process. Keeping those processes converged on a config
change is **not** the backend's job — it is the app's own
[worker bus](/concepts/worker-bus). Because a backend makes the deployment
multi-process, naming a `backend_module` requires the bus: set `TAI_BUS_REDIS_URL`
or the server refuses to start.

## Three ways a tool runs off the request path

- **Background** — submit a tool run and poll its result, for a run that outlives
  one request. The background tool-runs HTTP surface loads as a router module.
- **Scheduled** — schedule a tool to run later or on a cadence. A schedule names
  the base `tool_name`, its `tool_kwargs`, and a typed `cadence` (an interval or a
  crontab). The tool must carry the backend's `schedule_task` extension to be
  scheduled on a cadence — see the [schedule-a-tool guide](/guides/schedule-a-tool)
  for attaching it.
- **Distributed** — the worker backend spreads runs across workers.

Manage schedules from the CLI:

```bash
tai schedules list
tai schedules add report --cron '0 9 * * *'
tai schedules delete <name>
```

## The job budget

Every backend bounds a dispatched job by one setting, the dispatch group's
`task_timeout` (`<PREFIX>_TASK_TIMEOUT`, 300 seconds by default): it is the longest a
job may run on the worker, and how long a synchronous dispatch waits for its result.
It covers every job the worker runs — a dispatched task, a schedule fire, a callback.
Celery applies it as `task_time_limit`, RQ's worker sets it as the timeout of every job
it runs (whatever timeout the job was stored with), and arq as the worker's
`--job-timeout` default. The worker binds it when it starts, so a change converges
through a process recycle.

A backend never retries a tool body. A tool that wants retries declares a
[`ToolRetryPolicy`](/concepts/tools-and-extensions#retrying-a-tool-call), applied by
the platform's dispatch seam on every door. What a backend still retries is its own
transport — publishing a message on connection loss, reconnecting to its broker.

## Writing a scheduling backend

The scheduling protocol is declared once, in `tai42_contract.backend.scheduling` (also
re-exported by `tai42_kit.backend`). A backend that implements it is a scheduling backend
the schedules door, the CLI, Studio and backups work with unchanged:

- **The tools.** Register `backend_list_schedules` and `backend_delete_schedule` (their
  presence marks scheduling as available), and the backup pair
  `backend_export_schedules` / `backend_import_schedules`.
- **The extension.** Register a `schedule_task` `BACKEND` extension that branches a tool
  into `<tool>_schedule_task`. The door dispatches that branch with the schedule's name
  under `backend_schedule_name` and the dumped `ScheduleCadence` under `backend_schedule`;
  validate it back with the contract's `ScheduleCadence`.
- **The shapes.** The list tool returns `ScheduleListRow` dumps (name, tool, cadence,
  enabled, next run, an optional `error` — never the stored arguments); export returns
  `ScheduleRecord` dumps; import takes `ScheduleRecord` rows and a `skip`/`overwrite`
  mode and returns a `ScheduleImportReport`, reporting a bad row in its `errors` rather
  than dropping it.
- **Your own keys.** A queued job carries the target tool under your backend's own
  tool-name key. Split it out into the record's `tool` on export and list, and inject it
  back on import; the platform reads only `tool`.
- **What you cannot honour, refuse.** A backend that cannot honour an interval's
  `relative` flag refuses it on create, update and import with a clear error.

`tai42_kit.utils.runtime.normalize_schedule` parses the friendly specs a backend's own
tools may accept (seconds, a crontab string, `{"type": "interval", "every": 5, "period":
"minutes"}`) into the contract's cadence.

## Routing a tool to a backend

A tool is routed to a backend with a `BACKEND`-kind
[extension](/concepts/tools-and-extensions) — the extension kind whose job is to
send a tool's execution through a backend rather than running it inline. The tool's
definition does not change; the extension decides where it runs.

<Warning>
A tool that depends on a managed `stdio` MCP server's tools runs on the ASGI, arq,
and RQ execution paths, but not inside a Celery **prefork** worker child: the
managed server's live stdio subprocess connection does not survive the prefork
fork, so those tools are unavailable there. Route such a tool to a non-prefork
engine, or run it inline on the request path.
</Warning>

<Note>
A persist-across-jobs backend — a Celery **prefork** pool, whose forked children
hold their own in-memory caches for the life of the child — turns its pool over
**once** after any template-eviction or registry-mutating fleet op reaches it over
the [worker bus](/concepts/worker-bus), so a child never keeps serving a stale
compiled template or a stale registry from before the change.
</Note>

<Note>
A specific worker backend's setup — its broker, queues, and concurrency — lives in
that backend package's own repository, reachable from the
[Plugins section](/plugins). The platform documents the backend contract,
not any one engine.
</Note>

See the [schedule-a-tool guide](/guides/schedule-a-tool) and the
[HTTP API reference](/reference/api/index) for the tool-run and schedule routes.
