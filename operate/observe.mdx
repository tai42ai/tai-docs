Collect metrics and traces from a running server, and enumerate its runs.

The runtime records what runs. Tool and agent runs produce traces; aggregate counts and latencies roll up into metrics; a platform-side runs index enumerates every preset run. You query all three from the CLI. A monitoring backend plugin persists and serves the metrics and traces; the `monitor` extension traces a standalone tool call as one span.

## Query metrics

Query aggregate metrics over a time range. `--from` and `--to` take an ISO instant or a relative token (`7d`, `30d`); `--granularity` is `hour`, `day`, or `week`.

```bash
tai obs metrics --from 7d --granularity day
```

## List and read traces

<Steps>
  <Step title="List runs">
    List observability runs, or download the filtered list with `--export`.

    ```bash
    tai traces list
    ```
  </Step>
  <Step title="Read one trace">
    Get one run's full trace, or download it as JSON with `--export`.

    ```bash
    tai traces get <run-id>
    ```
  </Step>
</Steps>

Narrow the list to one subject with the [identity
dimensions](#the-identity-dimensions) the runtime stamps: `--user`, `--session`,
and `--version` filter to one person, one conversation thread, or one preset
version.

```bash
tai traces list --user person_7f3a --from 7d
```

## Reading traces

A trace is a tree of spans. Every span carries a neutral **kind** the monitoring
backend maps its own observation types onto:

| Kind | What it is | Studio body |
| --- | --- | --- |
| `LLM` | a model call | the messages, one bubble per message |
| `TOOL` | a tool call | Arguments / Result |
| `CHAIN` | a step that runs other work: a graph node, a run's root | Input / Output |
| `EVENT` | a point-in-time marker | Input / Output |

A span reports its token counts as `inputTokens`, `outputTokens` and `totalTokens`,
each `null` when the producer reported none. A model call's input and output are
recorded in the OpenTelemetry GenAI message shape — a list of `{role, parts}`
messages, each part a `text`, a `tool_call`, a `tool_call_response` or another typed
part, and an output message's `finish_reason` — and the Studio renders each part by
its type. A value that is not in that shape shows as a JSON tree, so every value
stays visible.

**Download resolved** in the trace view exports the whole trace with every reference
resolved. A value marked `{"$tai42_unrecorded": true}` was produced while monitoring
was off; the Studio notes it under the tree.

Read the span tree without the span inputs and outputs — the light read for walking
a run's steps by `parentId` before opening a value:

```bash
tai traces outline <trace-id>
```

```bash
GET /api/observability/runs/{trace_id}/trace/outline
```

It serves every span of the trace with its parent, kind, status, timing, token
counts and producer metadata. It costs the backend what the full trace read costs;
only the response is smaller.

### What the backend serves

Each monitoring backend declares the largest run-list page it serves, the run-list
sorts it serves, and the filters each sort cannot be combined with. The run list
caps `pageSize` to that page maximum (never refusing a larger one), the export
drains pages of that size, and the Studio offers only the served sorts and disables
a filter the active sort cannot carry — a shared link that combines them drops the
sort.

```bash
tai traces capabilities
```

```json
{
  "pageSizeMax": 100,
  "sortKeys": ["createdAt", "cost", "latencyMs", "totalTokens"],
  "incompatibleFilters": {"cost": ["maxCost", "minCost", "status", "version"]},
  "metrics": {"measures": ["cost", "count", "latency", "tokens"], "dimensions": ["model"]}
}
```

(`GET /api/observability/capabilities`; the example is shortened.) A sort or
combination outside the declaration is refused by the backend with `501`.

## List runs without the vendor

The platform keeps its own **runs index**: one row per registered-preset run,
persisted in the platform's own Postgres — so a deployment enumerates its runs
without reaching for the monitoring backend at all. Each row carries the
run id, the preset name and version, the run's [attribution](#attribute-a-run-and-roll-up-cost)
user and session, its outcome, its start/end window, and the monitoring
`traceId` as a deep link into the full trace.

```bash
tai runs list --preset support --outcome error
```

Filter by `--preset`, `--version`, `--user`, `--session`, `--interaction`,
`--outcome`, and a `--from`/`--to` start-time range; the same filters ride
`GET /api/runs` as query params. Outcomes are `running`, `success`, `error`,
`parked`, and `aborted` — a cancelled run records `aborted`, never `error`, and a
crash-interrupted run stays honestly `running` with no end time.

A run that parks on an async question and resumes later is two dispatches — two
rows. The shared `interactionId` joins them: the parked row records the
interaction it parked on, the resume's row records the same id, and
`--interaction <id>` returns that park's lifecycle pair.

A run that **resumes or takes** parked interactions itself — a door or tool
resolving [caller asks](/concepts/asking-the-caller) — records each id it acted on in
its `resumedInteractions` list, across its whole dispatch span, nested inline resumes
included (an inline resume opens no row of its own). The list is empty when the run
resumed nothing.

Rows are kept forever by default. Set `TAI_RUNS_INDEX_RETENTION_DAYS` and call
the prune on a cadence to bound the table:

```bash
tai runs prune
```

<Note>
Only a **registered preset** run lands in the index, stamped once at the
outermost dispatch — a nested sub-preset adds no second row, and a raw tool call
none. The index is fail-safe: a store outage never breaks a run.
</Note>

## One run, one trace

A run that dispatches nested work keeps a single trace. A subflow invoked as a
tool and an agent driven as a flow node join the dispatching run's trace — their
spans nest inside it rather than minting a fresh, orphaned trace — so one participant
interaction reads end to end as one trace. A run that parks on an async question
and resumes later — days later, on another worker — rejoins its original trace.

One **feature** run is one trace, however many sub-runs it fans into internally.
An agent that drafts then critiques then finalises, or one that polls several
voters before a judge, nests every sub-run inside the feature's one trace rather
than opening a separate root per sub-run — so the whole feature run reads as a
single tree, with the sub-runs as nested spans.

A run dispatched directly — through the sync run-tool API, a background or
scheduled tool run, or the MCP `tools/call` edge — opens its own trace root when
no trace is already open, and nests under the existing root otherwise. That
decision is made once at the shared run chokepoint where the run record is
registered, agnostic to what the preset wraps. Every runs-index row therefore
carries a `traceId` deep link whenever a monitoring backend is active; with the
no-op default there is no trace to link.

## Every feature's model calls

Every platform feature's model calls are traced. The monitoring callback is
attached once at a shared seam that every agent kind passes through, so a
model-usage span lands on the run's trace whatever the kind — a flow-driven
agent, a multi-phase agent, or a voter-and-judge agent — and a new agent kind
inherits the coverage without wiring of its own. An agent that runs its model
calls inside its own sandbox session bypasses that seam and is covered a
different way, emitting its own usage (see the sandbox note under [Attribute a
run](#attribute-a-run-and-roll-up-cost) below). Model calls made inside a
**tool** are not a feature: trace those with the [`monitor`
extension](#trace-a-standalone-tool-call) instead.

The **classifier** is a feature's model call too, but it is its own model kind,
not a chat model, so it carries no chat-model callback. Each classifier call
still records a model-usage span on the run's trace — its model id, token usage,
provider request id, and the call's latency — resolved onto the run's trace by
the same lineage rule, or onto a fresh root for a standalone call. **Embeddings**
are not recorded as model calls.

## Send outcomes and delivery receipts

Every outbound channel send made inside a run's trace — a flow's `notify_user`
send, a question delivered to a person, an inbound participant notice — records a
`send:{channel}` span around the provider call. The span carries the recipient
as its input, and the `notify_user` seam adds the provider's message ids as its
output; a raised error marks it `ERROR` with the failure detail: `error.type`,
`error.kind` (`unknown` for an unclassified exception), `retryable`, and a
positive `retry_after` the medium asked for, stamped only alongside
`retryable: true`. A seam that retries emits one span per attempt, stamped with
`retry.attempt`, and there `retryable` is the seam's own decision: `true`
exactly when another attempt follows, `false` on the last one (the attempt
budget is spent, or too little of the ask's window is left for the backoff). So
"attempt 1 failed retryable, attempt 2 accepted" is visible rather than
collapsed. On a single send, `retryable` is the error's own classification
(`false` for an input error). A tool dispatched under a retry policy records the
same keys on each `tool-attempt:{tool}` span. These keys are ordinary span
metadata.

Acceptance is not delivery. On channels with a delivery-status webhook (WhatsApp,
Twilio), the provider's later status closes the loop: the status is resolved back
to the originating send and posted as a `delivery_receipt` event on that run's
trace, nested under its send span — a failed delivery as an `ERROR` event
carrying the provider's error detail. The receipt is **observability only**: it
annotates the trace, never re-sends, and never fails the flow.

<Note>
A [conversation-bridge](/reference/conversation-bridge) reply is covered by
**receipts, not spans**. Bridge delivery runs in a detached task after the turn's
trace has closed, so a span there would attach to no run; the record's own delivery
ledger and its delivery-status receipts are the authoritative accepted-versus-
delivered signal for bridge messages instead. A `failed` from a reachable-channel
refusal of a turn's reply also sends the participant a best-effort could-not-deliver
notice — its own failure logged at `ERROR` and never retried — while a
transport-exhaustion `failed`, or a refusal of an operator's hand-injected send, sends
none; the failed-delivery listing and the trace event remain the signal either way.
</Note>

<Note>
The webhook wiring and per-channel status semantics live on the channel plugin
pages: [channel-whatsapp](/plugins/tai42/channel-whatsapp) and
[channel-twilio](/plugins/tai42/channel-twilio). A send outside any trace emits
no span — a rootless span would attach to no run.
</Note>

## Trace a standalone tool call

A tool call outside a flow or agent has no trace of its own. Load the `monitor` extension and stack it onto a tool to record the call as one live span. Load the module, then attach `monitor` to a tool.

```yaml manifest.yml
extensions_modules:
  - tai42_skeleton.extensions.builtin.monitor

tools:
  - title: my_tools
    module: myapp.tools
    include: [greet]
    extensions:
      greet: [[monitor]]
```

When a flow or agent trace already owns the call, the extension suppresses its own span and just runs the tool.

<Note>
Metrics and traces are served by a monitoring backend plugin, registered under `monitoring_module`. Without one, the runtime uses a no-op default and there is nothing to query.
</Note>

## Attribute a run and roll up cost

Every run's trace can be tagged at the shared run chokepoint with the run's own
identity — the flow kwargs the operator defines per delivery, carried verbatim as
a `RunAttribution` of tags and metadata, wired once at the shared seam so every
door attributes. The attribution is set on the trace from its first span, so it
covers the whole run — the user, session, tags, and version are on the trace
before the first model or tool span opens, not attached to the later spans
alone. That lets you **group** cost and tokens by identity when you
query traces: per-delivery attribution, with no tenant system and no
per-tenant isolation — attribution only. Metrics aggregate over a time range
alone — `tai obs metrics` takes no identity filter, so slice by identity on the
trace list and roll the cost up from there.

There is **no cost-aggregation module**. Cost aggregation is a flow or a view built
over these attributed traces: the platform ships the generic attribution enabler,
and assembling spend into a cost view is delivery work on top of the trace data.

### The identity dimensions

Beyond the per-delivery tags, the runtime stamps every conversation-driven run
with generic identity at the same shared seam, and the monitoring backend maps
them to its native trace dimensions:

- **`user_id`** — person-id-first: a run with a resolved
  [person](/guides/link-a-person-across-channels) is attributed by that person's
  stable `person_id`, so one human's runs group together across channels. With no
  person it falls back to the raw `{channel}:{address}` the door saw, or the bare
  address on the API door.
- **`session_id`** — the resolved conversation thread, so a whole back-and-forth
  reads as one session.
- **`tags`** — the conversation route as `route:{name}`; a registered preset
  dispatch adds `preset:{name}` and `preset-v:{version}` and lifts the version
  onto the trace's native version dimension. Only the **outermost** preset
  stamps: a nested sub-preset never pollutes the root identity, and a draft run
  carries no preset stamp at all.

The run list filters by exactly those dimensions: `GET /api/observability/runs`
takes `user`, `session`, and `version` params, plus any number of
`meta.<key>=<value>` params — each one a string-equality clause on the trace's
metadata.

<Warning>
That identity is personal data, and it lands in **your** monitoring backend — so
retention and erasure there are yours to govern. The platform sets no trace
retention on your behalf, and [forgetting a
person](/reference/conversation-bridge#forgetting-a-person) erases the bridge's
own stores, never the monitoring backend's traces. Set a deliberate retention
policy, and honour an erasure request by deleting the subject's traces keyed on
their `user_id` — person-id-first attribution keeps a linked subject's
cross-channel history under one deletable key. See the
[monitoring-langfuse](/plugins/tai42/monitoring-langfuse) page for the
backend-side duties.
</Warning>

<Note>
Because the Claude Agent SDK's model calls run inside the sandbox session and
bypass the platform LLM seam, the [`claude_code`](/guides/use-the-ready-made-agents)
adapter emits the SDK-reported usage and cost into the active trace itself — so an
attributed `claude_code` run's spend rolls up with everything else. Run standalone
with no ambient trace, the adapter mints its own root trace carrying that
model-usage span, so a standalone sandbox run is observable on its own rather than
emitting nothing. The boundary:
the toolbox `prometheus_metrics` extension records latency and count only; it is
not the cost seam.
</Note>

## The monitoring pipeline

Every monitoring backend records through one OpenTelemetry writer: each serve and
backend process exports OTLP over HTTP to an **OpenTelemetry collector** running as
its own container. The process encodes each recorded value once on the caller's
thread and hands spans to the SDK's batch processor; the protobuf encoding and the
network send run on the processor's worker thread, and the collector does the
batching, retrying, mapping to the backend's vocabulary, and the send. A deployment
changes backend by changing the collector's exporter and transform; the
[monitoring-langfuse](/plugins/tai42/monitoring-langfuse) page carries the Langfuse
mapping.

### Writer settings

The writer reads the OpenTelemetry SDK's own standard environment — no
platform-specific names.

| Variable | Required | Read by |
| --- | --- | --- |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (or `OTEL_EXPORTER_OTLP_ENDPOINT`) | yes — boot refuses without it | the OTLP exporter |
| `OTEL_PYTHON_SDK_INTERNAL_METRICS_ENABLED=true` | yes — boot refuses without it | the batch processor's drop counter |
| `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES` | no | the record resource |
| `OTEL_BSP_MAX_QUEUE_SIZE` / `_SCHEDULE_DELAY` / `_MAX_EXPORT_BATCH_SIZE` | no (2048 / 5000 / 512) | the batch processor |
| `OTEL_EXPORTER_OTLP_TRACES_TIMEOUT`, `…_COMPRESSION`, `…_HEADERS` | no | the OTLP exporter |
| `OTEL_METRIC_EXPORT_INTERVAL` | no (60000) | the drop-count collection; every flush collects too |

The value-length limits (`OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT`,
`OTEL_SPAN_ATTRIBUTE_VALUE_LENGTH_LIMIT`) have no effect: a recorded value is never
truncated.

### Each value recorded once

A model call records its input and output messages in full, in the OpenTelemetry
GenAI message shape, plus the generated message's full record; a tool call records
its arguments and result in full. A chain record (a graph node, its root) never
copies the run's data: a value already recorded appears as a **reference** to the
record that first holds it, the one-key object
`{"$tai42_ref": {"span_id", "field", "pointer"}}` (with a `trace_id` when the record
is in another trace). `{"$tai42_unrecorded": true}` marks a value that exists but was
produced while nothing recorded. A reference resolves through the reader:

```bash
GET /api/observability/runs/{trace_id}/spans/{span_id}/resolved?field=input&pointer=/messages/0
GET /api/observability/runs/{trace_id}/trace/export?resolve=true
```

The first returns one field of one span (`pointer` is an RFC 6901 JSON pointer, empty
for the whole value) with every reference on the way and inside it resolved; the
second exports the whole trace resolved. The export's `resolve` is a boolean, `false`
when absent. `true`, `t`, `yes`, `y`, `on` and `1` read as true, and `false`, `f`, `no`,
`n`, `off` and `0` as false, each word in any case; any other value, the empty one and
one with surrounding spaces included, answers `400` with the field and the error type,
`{"error": [{"loc": ["resolve"], "type": "bool_parsing"}]}`. A reference the backend does not yet hold
(its ingestion is asynchronous) or has lost answers `502` with the reason "not yet
available or lost" — retry once ingestion catches up. Every `SecretValue` in a
recorded value is written as `[secret]`.

### Dropped and failed records are counted and alerted

Nothing the writer cannot deliver is silent. Every process counts it, and `/metrics`
serves the run family's totals:

| Counter | Counts |
| --- | --- |
| `tai42_monitoring_spans_dropped_total{reason="queue_full"}` | spans evicted by a full export queue |
| `tai42_monitoring_spans_failed_total` | spans in an export batch the collector did not accept |
| `tai42_monitoring_export_failures_total` | export calls that failed |
| `tai42_monitoring_attributes_dropped_total` | span attributes evicted over the span limit |
| `tai42_monitoring_records_failed_total` | records, or one field of a record, the writer could not build (an unencodable value is recorded as `{"$tai42_unencodable": "<type>"}`) |

Each growth of those totals raises one **`monitoring_export_failed`** platform event
within 15 seconds, whichever process of the family notices it first. Its payload is
the growth since the last alert:

```json
{"spans_dropped": 0, "spans_failed": 12, "export_failures": 1, "attributes_dropped": 0, "records_failed": 0}
```

Bind a [hook](/concepts/hooks) on the topic to decide what an operator sees. The
hook's own run records nothing, so a dead collector never feeds itself. Readiness is
not tied to monitoring: a monitoring outage never pulls a serving worker.

The collector counts its own side on its telemetry endpoint (port `8888`). Alert on:

- **`otelcol_exporter_queue_size`** against `otelcol_exporter_queue_capacity` — the
  batches waiting to reach the backend. The collector retries a send it cannot make
  until it is delivered, so a backend that is down or unreachable (or an unset
  `LANGFUSE_HOST`) fails no span: the collector stays ready, logs each retry at
  `INFO`, and only this queue grows. A queue that keeps growing is the signal.
- **`otelcol_exporter_enqueue_failed_spans`** — spans refused because the queue is
  full.
- **`otelcol_exporter_send_failed_spans`** — spans the backend refused for good,
  logged at `ERROR` and dropped (for example, a missing or wrong
  `OTEL_COLLECTOR_LANGFUSE_AUTH` answered `401`).
- **`otelcol_receiver_refused_spans`** and **`otelcol_processor_refused_spans`** —
  spans the collector refused on intake (for example, over its memory limit).

### Write a monitoring backend

A backend plugin implements a **reader** for its backend and registers the shared
writer with it:

```python
from tai42_contract.app import tai42_app
from tai42_kit.monitoring.otel import OtelWriter


@tai42_app.monitoring.register_monitoring
def my_monitoring():
    return MyMonitoring(
        writer=OtelWriter(resource_attributes={"deployment.environment.name": "prod"}),
        reader=MyReader(),
    )
```

The reader implements `MonitoringReader`. Beside the reads, it declares what it
serves and maps its own vocabulary onto the neutral one:

- `get_observation(trace_id, observation_id)` returns one observation with its full
  input and output — the call references resolve through.
- `list_capability()` returns a `ListCapability`: the `OrderBy.field` values
  `list_traces` serves, and for each sort the `MonitoringFilter` field names it cannot
  combine with. `list_traces` raises `MonitoringReadNotSupportedError` outside it.
- `max_page_size()` returns the largest `limit` one `list_traces` call accepts; a
  larger `limit` raises `ValueError`.
- Each `MonitoringObservation` carries a `kind` (`LLM`, `TOOL`, `CHAIN` or `EVENT`)
  mapped from the backend's own observation type, and the `input_tokens`,
  `output_tokens` and `total_tokens` the producer reported.
- Each `MonitoringTraceSummary` carries the trace's own `input` and `output`; the
  platform bounds them for the run list.
- `list_spans_in_window` selects steps by the producers' marker, never by span
  names: a record whose metadata `tai42.step_role` is `grouping` or `sub_step` is
  never an item, and neither is a model call nor an event.

The backend's attribute vocabulary lives in the collector config, never in the
process. Registration refuses a backend whose writer or reader lacks a member of its
protocol, naming the members.

## Pending state saves

The [state store's pending saves](/concepts/states#pending-saves) publish Prometheus metrics on
the server's `/metrics` (the multiprocess-aware registry). Counters:
`tai42_state_outbox_enqueued_total`, `tai42_state_outbox_applied_total{phase}`,
`tai42_state_outbox_attempt_failures_total{phase,kind}`, `tai42_state_outbox_failed_total{phase}`,
`tai42_state_outbox_divergences_total` (an apply whose answer differed from the run's
projection), `tai42_state_outbox_discarded_total`, `tai42_state_outbox_retried_total`,
`tai42_state_outbox_lock_waits_total`, `tai42_state_outbox_notify_failures_total`,
`tai42_state_outbox_sweep_errors_total`, and `tai42_state_outbox_drain_waits_total{door}`
(`door` is `read` or `run_entry`). Histograms: `tai42_state_outbox_drain_wait_seconds{door}` and
`tai42_state_outbox_apply_latency_seconds` (enqueue to records applied). Gauges, set by each
sweep pass: `tai42_state_outbox_rows{status}` and `tai42_state_outbox_oldest_age_seconds`.

Set alert rules on three of them: any increase of `tai42_state_outbox_failed_total` (a save
failed and holds its subjects), `tai42_state_outbox_rows{status="failed"}` above zero (a held
save still waits for an operator), and `tai42_state_outbox_oldest_age_seconds` above a few sweep
intervals (saves are not being applied). The failed save itself is listed under
`tai states pending-saves list --status failed`.
